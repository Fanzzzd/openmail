# Mobile development

`apps/mobile` is an Expo SDK 57, React Native 0.86.3, TypeScript and expo-router project. The UI calls only the Mailbox from `@openmail/core/portable`. SQL, migrations, provider HTTP and token exchange stay in core. The OS adapters are in `src/platform`, and the structured op-sqlite adapter is in `packages/core/src/platform/react-native`. Core does not depend on React Native.

## Local checks

Run from the repo root:

```sh
pnpm install --frozen-lockfile
pnpm build
OPENMAIL_LOW_MEMORY_TESTS=1 pnpm test
pnpm exec oxlint
pnpm exec oxfmt --check .
```

The mobile `build` only compiles the Lingui catalogs and checks TypeScript. It does not generate the iOS or Android projects and does not start Metro. The tests use Vitest, Expo/RN mocks and a Node SQLite shim. `pnpm check-types` also covers mobile. pnpm keeps its isolated install. Expo Metro discovers the real symlink paths of the workspace and core on its own, and autolinking picks the mobile React/native dependencies. `metro.config.cjs` rejects the desktop core entry. Do not switch the workspace to hoisted.

## Running in the simulator

You need macOS, Xcode with an iOS Simulator runtime, and CocoaPods. Metro loads `@openmail/core/portable` from core's `dist`, and the Lingui catalogs must be compiled first, so build from the repo root first:

```sh
pnpm build --filter=@openmail/mobile...
cd apps/mobile && pnpm exec expo run:ios
```

On its first run, `expo run:ios` uses `app.config.ts` to generate the git-ignored `ios/`, runs `pod install`, builds a debug development build, installs it in the simulator and starts Metro. When native code has not changed, later runs only need `pnpm start` in `apps/mobile`. `--device "<simulator name>"` picks the simulator.

IMAP accounts need no environment variables. Gmail and Outlook sign-in need the client IDs you registered yourself, listed in the [client configuration](#client-configuration) table. The simulator uses only these iOS entries:

```sh
export EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID=<your own Google iOS client ID>
export EXPO_PUBLIC_MICROSOFT_CLIENT_ID=<your own Microsoft public client ID>
export OPENMAIL_IOS_BUNDLE_ID=<bundle ID entered at registration>  # default com.openmail.mobile
```

`app.config.ts` writes these values into `extra.mobileOAuth`. Metro reads them at startup, so restart Metro after a change. The callback scheme and bundle ID are written into the native project. After changing the client ID or bundle ID, run `pnpm exec expo prebuild --clean --platform ios`, then `pnpm exec expo run:ios`. A provider without a client ID cannot sign in.

## Database

`@op-engineering/op-sqlite` is pinned at 18.2.5. The SQLite in the published package's `cpp/sqlite3.h` is 3.53.4. `op-sqlite.fts5=true` in `package.json` turns on the compile option, and `iosSqlite=false` uses the bundled version. FTS5 trigram needs SQLite 3.34.0 or later. At startup the app creates a temporary trigram table to verify the actual native build, then turns on WAL and runs all of core's migrations; see [db/migrations.ts](../../packages/core/src/db/migrations.ts). Startup stops if the tokenizer is missing. The vector capability reports `vectors=false`.

The Effect `SqlClient` uses one connection, the SQLite compiler, `BEGIN IMMEDIATE`, savepoints and a semaphore. It releases the connection only after an async statement completes, so a cancelled request leaves no stray write. The tests emulate the op-sqlite Promise/result API with real Node SQLite. They cover migration idempotence, FTS integrity, upsert rowid, paging, transaction rollback, recovery from a failed COMMIT and serialization of concurrent work. The shim cannot prove native JSI, WAL, device storage or locking behavior. A development build must verify those later.

Database startup goes through core's `MobileDatabaseRecovery` Effect service, which runs `PRAGMA quick_check` on a read-only op-sqlite connection before migrations. The foreground inspect passes its result to open, and the same process reuses a successful check. The foreground quick_check result and the actual check time are saved in `mail.db.foreground-check.json`. A cold headless start reuses only a success record from the last 30 minutes. A failed, expired, corrupt or future-dated record triggers a new check. A background check does not extend the foreground record's time. Before reuse, the app still checks the recovery marker, the quarantine copy state and whether the main database exists. The first foreground entry of a new process still runs an actual check. An integrity failure shows the recovery screen, and recovery starts only after the user taps "Rebuild local database". Disk, permission or lock errors only stop startup and are not treated as corruption to reset. The foreground and headless Mailbox share an in-process recovery gate. The gate refuses to install a new database while a connection is open, and the background never recovers on its own.

Recovery first keeps the main database, WAL, SHM and journal with Expo `File.copy()`. After all copies finish, it writes the quarantine copy metadata, then migrates a separate new database and salvages readable records using the same user table list as desktop. A retry after failure reuses that complete copy, so it does not take the space of the whole database again. It copies again only when a newer generation of the original database is corrupt. The rebuild entry orders candidates as follows: the explicitly protected object, the newest complete preserved copy of the current original database, the copy an old report refers to, then other complete copies. After install it always protects the original copy named by the current report directly, even if that copy's metadata is lost or incomplete. While the main database still exists, unfinished copy files are deleted. Only when the main database is gone and no complete copy exists does the app keep one unclassified quarantined main file for salvage. An unreadable optional parent record can be set to null, and records that are still copied do not count as skipped. Only records that cannot be kept count as skipped. Accounts, drafts, preferences and queues are kept where possible, and SecureStore does not change. Cache, FTS and vector tables are not copied. Sync cursors, sync times and errors are cleared, and after the user continues, the existing foreground provider full sync rebuilds them. When the whole database is unreadable, the result is an empty account list and the user must add accounts again. The original database stays in the persistent mail directory as `mail.db.corrupt-*`.

Before install, the app writes a temporary file in the same directory, then renames it to `mail.db.recovery-state.json`. It replaces the main database only after closing the new database in DELETE journal mode. Expo move does not overwrite an existing file by default, so the app deletes the old path before the move, and the marker blocks every opener during that time. After an interruption, the recovery screen can continue with the prepared new database. If the new database was already moved, the app verifies the main database first and then finishes. The recovery result is saved in `mail.db.recovered.json` and shows the copied and skipped counts. Android also shows the original database's file name. iOS does not show the file name because it is not accessible. After the user continues, the app marks the report as read and keeps its backup reference so later cleanup protects it. The protected object can be replaced only after the next complete copy is committed. A failed preparation clears the unfinished new database and sidecars and keeps the original database or quarantine copy. If rename fails after the main database is removed, the app keeps the verified new database and the marker, and the next startup continues the install. A valid marker left by an interrupted process can also continue the install. If the marker is torn or unreadable, or the replacement database truly fails integrity, the app deletes only the marker, keeps the other files and returns to corrupt, and the user can rebuild again. A transient open or read error on the replacement database returns unavailable and keeps the marker and replacement database for a retry. Stale new databases are cleaned up only on retry. When the main database is gone, the app salvages from the quarantine copy. Prepared files without a valid marker are never opened as the main database. The file layer has no fsync or cross-process lock guarantee, and the unit tests cannot prove durability across power loss, native WAL or device locking behavior.

Recovery uses only `open({name, location, readOnly})`, `execute` and `close` from the installed version, plus Expo `File.copy()` and `File.move()`. It does not assume an op-sqlite backup API. Sources: [op-sqlite API](https://op-engineering.github.io/op-sqlite/docs/api/), [Expo FileSystem](https://docs.expo.dev/versions/latest/sdk/filesystem/). The SQLite shim is in `packages/core/test-support` and is not part of the core build. File fault mocks cover space control under repeated failure, the atomic marker, fallback on a corrupt marker or replacement database, the process check cache, and background re-checks after expiry or failure. They also cover record salvage, quarantine copies, retry after interruption, the connection gate and provider resync.

Sources: [op-sqlite installation and FTS5 configuration](https://op-engineering.github.io/op-sqlite/docs/installation/), [SQLite 3.34.0](https://www.sqlite.org/releaselog/3_34_0.html).

## Client configuration

Use only mobile clients you registered yourself, and do not fill in a secret. The steps are in [Google](../../docs/setup-google.md#mobile) and [Microsoft](../../docs/setup-microsoft.md#mobile). The settings are:

| Environment variable                     | Content                                                          |
| ---------------------------------------- | ---------------------------------------------------------------- |
| `OPENMAIL_IOS_BUNDLE_ID`                 | iOS bundle ID, default `com.openmail.mobile`                     |
| `OPENMAIL_ANDROID_PACKAGE`               | Android package name, default `com.openmail.mobile`              |
| `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID`       | Your own registered Google iOS client ID                         |
| `EXPO_PUBLIC_GOOGLE_ANDROID_CLIENT_ID`   | Your own registered Google Android client ID                     |
| `EXPO_PUBLIC_MICROSOFT_CLIENT_ID`        | Your own registered Microsoft public client ID                   |
| `EXPO_PUBLIC_MICROSOFT_ANDROID_REDIRECT` | The full `msauth://<package>/<encoded-signature>` URI from Azure |

`app.config.ts` generates the Google reversed client ID scheme, the iOS `msauth.<bundle>://auth` scheme and the Android intent filter. The client IDs in the environment variables are public registration data. The refresh token never goes into config, the database or logs. expo-secure-store saves it only to the device's secure storage. Uninstalling the Android app deletes the secure storage. Whether iOS Keychain items survive uninstall is up to the system.

OAuth uses the system browser, PKCE S256, a random state, a five-minute timeout and a native scheme callback. Token exchange goes through the fetch HttpClient, and error bodies are not returned to the UI. Outlook uses only `consumers`. Expo Go cannot provide custom native modules or these callbacks, so later tests must create a development build. Real authorization, the simulator, Metro and EAS still need acceptance on a development build.

## Mail actions

The UI stays single-column, with three levels of navigation: account and mailbox, thread list, and reader. Compose uses its own modal, and settings open from the account screen.

- Organizing reuses `modifyWithUndo`, `snoozeWithUndo` and `undoBatch` from `mailbox.organize`: archive, trash, read/unread, star, Gmail labels or Outlook move, and snooze. It supports multi-select, a long-press menu and VoiceOver actions. A short swipe is 60pt and a long swipe is 180pt, left and right, each configured in settings. Vertical scrolling and dragging back to the start run no action.
- Compose supports new mail, reply, reply all and forward. Recipient suggestions query only core's local contacts. With text selected, the user can apply bold and italic, and bulleted lists are supported. With no text selected, the style applies to the whole message. Reopening a draft restores style ranges and lists from the sanitized HTML, and the first edit keeps the formatting. The HTML and message text are normalized by the same compose sanitizer as desktop. Core fetches forwarded attachments.
- Files come from the document picker and photos come from the system photo library. The app does not request camera permission. Photos are decoded and re-encoded as JPEG first. PNG keeps transparency and is re-encoded as PNG. The original file's EXIF and GPS are removed before the base64 read. Turning off the picker's exif return value does not replace re-encoding the file. Files are stored only in the device database. After the read finishes, fails or exceeds the limit, a finally block deletes the picker's and the re-encoder's cache copies. It does not delete the original in the photo library. Existing and new attachments are capped at 15 MiB in total. Before queuing, the app reuses core's attachmentProblem to check Gmail's blocked attachments and Outlook's 3 MiB limit. A validation failure in an old queue shows "Rejected before sending." and is not marked as uncertain delivery. Portable MIME still has a 25 MiB total limit.
- Autosave runs every 600ms only after an actual edit. Writes are serialized, and leaving the screen saves the last edit. Unfinished recipient input is saved too. Opening new mail, reply or forward without editing creates no draft. The draft entry on the mailbox screen queries core's drafts mailbox, and the compose screen can discard the draft and its pending send intent. The app keeps core's draft queue. The mobile Layer's `localDraftQueue` blocks pushing drafts to the server, and attachments do not upload before an explicit send. The database lives in a persistent directory, so the system clearing caches does not delete local drafts or mail waiting to send.
- Sending asks for confirmation first, then waits 0, 5, 10, 20 or 30 seconds according to the shared preference. The send intent persists in a reserved key of the existing prefs table, with no new migration. Delivery reuses core's user/app send validation and audit. Undo keeps the draft. While offline, the mail stays pending and is handled on the next foreground or pull to refresh.
- The outbox separates definite failures from uncertain results. A definite failure can open the kept draft through "Retry send". An uncertain result requires checking Sent first and never resends automatically. The full rules for transactions, restarts and resend protection are in the [sync notes](../../docs/sync-correctness.md#持久发送意图).
- Search reuses the Gmail operator parser. With no local results it falls back to the server, and the user can also search the server directly. The app shows a fallback notice and notices for errors, truncation or ignored operators.
- Settings cover adding accounts, signing in again, enabling, disabling and removing accounts, the four swipe actions, the undo send time, the remote image default and the language. Remote images are blocked by default. When the user turns them on, only HTTPS images are allowed, and the limits on scripts, forms, fonts and navigation stay in effect.
- Lingui covers en, zh-CN, cs, nl, fr, de, it, ja, ru and es. Identical strings reuse the desktop translations, and message text fields keep their extraction comments. After a change, run `pnpm --filter @openmail/mobile i18n:extract`, fill in the translations, then run `i18n:compile`. The tests check catalog sync and missing translations.

## Foreground and background sync and native permissions

The first foreground entry, returning from the background and pull to refresh run core sync. Background refresh is off by default and can be turned on in settings. expo-background-task schedules it through iOS BGAppRefreshTask and Android WorkManager. The 15-minute minimum interval is only a scheduling hint. The OS decides when the task runs, and it is not real time. The background shares the portable Mailbox's Inbox incremental command, with a total budget of about 25 seconds split across accounts. An unfinished first sync, a missing or expired cursor, or an IMAP UIDVALIDITY change is left to the foreground. The background does no full sync or backfill and does not send or push the organize queue. The custom `index.js` imports the background task first, then the Router, so a headless start does not depend on loading routes. iOS checks NWPath's constrained and expensive flags and Low Power Mode. The Android worker requires an unmetered network and battery-not-low, and checks battery saver, so it runs only on unmetered networks. Android does not reschedule after a reboot. The user must open the app to restore it, because RECEIVE_BOOT_COMPLETED is blocked explicitly. There is no polling or push relay.

Local new mail notifications are opt-in per account and off by default. The foreground and background consume core's NewMail event. The first sync, mail older than the last sync and already seen mail that moved do not notify. Stable message IDs are kept in the existing prefs for 30 days to deduplicate, and cleanup goes by record time and account. An old boolean record gets one 30-day retention period on its first cleanup, and records of removed accounts are deleted. Regular compose.prefs reads exclude the whole mobile-background prefix. The app claims an item before submitting it to the OS, so a process exit between the two can miss one notification but never repeats one. The visible foreground Inbox is silent. The same account or thread reuses the notification ID. iOS groups by thread, and Android groups by account. Tapping a notification opens the thread through the existing `/reader` route. Notifications show only the sender and subject, never message text. Hide content is on by default, so a notification contains only the sender, even after unlock. With it off, the subject shows too. The sender and subject first have C0/C1 and bidirectional text controls removed and whitespace collapsed, then are limited to 80 and 120 characters. An empty sender falls back to the address, then to the localized "New mail". Android switches to a new PRIVATE channel and deletes the old PUBLIC channel, and the public lock screen version shows only the localized "New mail". The app requests system permission only when the user opts in to notifications or the badge, and does not request a remote push token. The system manages notifications already shown.

The app icon badge for unread Inbox mail is off by default. It uses core's local unread count and the thread grouping preference, and mail not in the cache does not count. The system or an Android launcher may not support badges or may limit them. A failed badge update does not revert the saved setting, and a later refresh tries again. Send delay is handled only in the foreground. After the app goes to the background, it starts no new send, but a transfer already started may finish. The undo send toast is separate from the organize undo toast.

Expo's default background-task iOS implementation uses BGProcessingTask. This project's dependency patch changes it to BGAppRefreshTaskRequest, and the plist adds only `UIBackgroundModes=fetch` and the `com.openmail.mobile.refresh` permitted identifier. The notifications patch removes the Firebase messaging service and the startup broadcast and adds native grouping on both platforms. A local config plugin allows only POST_NOTIFICATIONS and blocks the APNs entitlement, Firebase services and auto-initialization. Android still blocks RECEIVE_BOOT_COMPLETED, C2DM RECEIVE, CAMERA and RECORD_AUDIO, and image-picker turns off camera and microphone permissions. The tests check Expo introspect, the actual autolinking and the installed dependency sources. Task wakeup, system termination, notification taps, the lock screen and the badge are not yet verified on a real device.

Sources: [BackgroundTask](https://docs.expo.dev/versions/v57.0.0/sdk/background-task/), [Notifications](https://docs.expo.dev/versions/v57.0.0/sdk/notifications/), [ImagePicker](https://docs.expo.dev/versions/latest/sdk/imagepicker/).

The implementation is in [background.ts](src/background.ts), [background-policy.ts](src/background-policy.ts), and core's [mobile-background.ts](../../packages/core/src/mailbox/mobile-background.ts) and [mailbox-live.ts](../../packages/core/src/mailbox/mailbox-live.ts). Core manages the defaults and persistent deduplication. The native configuration is in [app.config.ts](app.config.ts) and [plugins](plugins).

## AI, snooze and signatures

AI is off by default. The app sends visible message text to Anthropic only after the user confirms per account. The API key is saved only through SecureStore, and the UI only queries whether one is configured. The model uses core's options. Thread summaries can be generated on demand. Automatic summaries run only when the thread is opened, after the user turns on that account's automatic option, and background refresh never calls AI. Asking about a thread preloads context from the same visible text pipeline. The assistant can propose archive, Gmail user labels and plain text drafts. The user reviews every thread, the real labels and the full draft on the mobile approval screen, then approves or rejects. The built-in assistant ignores the shared write permission and only ever creates proposals. An approved draft opens in compose, and sending still needs the usual manual confirmation.

Rewrite, shorten, and friendly or formal tone work only on the user's own message text before the signature and quote. The app shows the text before and after, and changes the current draft only after the user accepts. The signature, quote and unchanged parts keep their formatting. After accepting, if the message text has not changed since, the user can undo the AI edit and restore the earlier message text and formatting. If the draft changes after generation, the user must generate again. Leaving the screen, going to the background or turning off the account's authorization cancels the request. AI input removes hidden text. When the HTML CSS check exceeds its budget, the app omits the message text and adds the "Message too complex for AI" marker, so it never treats plain text derived from the HTML as a safe fallback. Search still keeps the full text. AI input contains no images, attachments or attachment-derived content. Output is shown in native Text and does not load links or images automatically.

Thread actions offer snooze presets, a date and time picker and cancel snooze, and the Snoozed mailbox queries the shared snooze table. Due snoozes wake on three triggers: before a foreground sync, from a local foreground timer every 30 seconds, and from background refresh when enabled. This works offline in the foreground too. The background also handles local due snoozes while offline, and provider writes still wait for a foreground sync. The app submits local snooze notifications only for accounts with notifications turned on and system permission granted. They follow the hide content setting and thread grouping. Each due time is deduplicated on its own. The OS decides when background tasks run, so on-time reminders are not guaranteed.

Settings can edit each account's default signature for new mail and for replies and forwards, reusing the shared signature library and defaults table. A new compose session inserts the plain text signature, and an existing draft keeps its saved content. No migration was added.

Outbound failure notices reuse core and show the action, subject, sender and reason. Resending only to rejected addresses opens a new draft. The rules are in the [sync notes](../../docs/sync-correctness.md#出站操作队列).

## Media adapter limits

The existing PDF extraction depends on `pdfjs-dist` 6.3.289 and runs in a disposable Node worker on desktop. The repo has no pure JS extractor verified to work on RN or Hermes. Hermes provides neither PDF.js's browser worker and DOM nor the Node worker, so mobile cannot reuse the desktop budgets of 32 MiB, 100 pages, 30 seconds and 128 MiB worker memory, or the forced termination. Today `PdfWorker` returns unavailable at once. It adds no new native dependency and does not upload PDFs for extraction elsewhere. A future native worker must follow the same budgets. Source: [browser and Node environments in the PDF.js examples](https://mozilla.github.io/pdf.js/examples/index.html).

The desktop `ImageNetwork` pins the public IP after DNS resolution and re-checks on every redirect. It rejects private networks, credentials, unusual ports and non-raster responses, and limits traffic and time. Mobile has no UI entry point that needs this port, and Expo/RN fetch cannot pin the address, so mobile keeps a no-op that refuses explicitly. Remote images in the reader take a separate path. They are blocked by default and allowed through the shared `shouldLoadRemote` and the per-message choice, and only the device WebView requests HTTPS images directly. cid images still download through core. Images, PDFs and media-derived content are never sent to AI or a third-party conversion service.

On-device inference is not supported. The existing implementation uses `onnxruntime-node`, Transformers and a Node child process. Mobile has no matching native runtime, terminable inference worker, Vision or sqlite-vec Layer. With `vectors=false`, the index capability is unavailable. The app does not download models or fall back to cloud media inference. The per-account opt-in Anthropic feature for visible message text is described in the AI notes above.

## Backup and the lock screen

The mail database, WAL, SHM, local drafts, send intents and core files are stored in `Paths.document/openmail-data`. They do not use the cache, which the system can clear. At startup the app first migrates the old `Paths.cache/openmail` as a whole directory, keeping DB, WAL and SHM. Without a cache directory, it migrates the old Documents/openmail. When a persistent database already exists, the app does not overwrite it and moves leftover copies into a separate legacy subdirectory inside the persistent directory. An empty target directory lets the migration continue after an interruption.

The iOS local Expo module `modules/openmail-storage` synchronously sets and confirms `URLResourceValues.isExcludedFromBackup` before moving directories and before opening the database. It allows only three fixed mail directories. If the module is missing or backup exclusion fails, database startup stops. Linking the module needs a regenerated development build. Autolinking and Swift syntax are checked. Attribute inheritance, directory migration and native module calls are not yet verified on a real device. Android still sets `android.allowBackup=false`. The reader uses an incognito WebView.

New SecureStore items use `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`. SecItemUpdate does not change the accessibility of existing items on its own. After an iOS foreground unlock, before network checks and sync, the app migrates account secrets and core's model and update keys one at a time. It writes and verifies a temporary copy, deletes the old item, recreates and verifies it with the new attribute, then records a completion marker and cleans up the copy. Reads and writes of the same key are serialized. After a failure or process exit, the app can read from the safe copy and retries on the next foreground entry. It does not migrate in a headless task. Old items not yet migrated may still be unreadable while the device is locked. When the device is locked or secure storage is unavailable, a read returns a retryable `ProviderError`. The app does not treat it as a revoked credential and does not delete the token, and the error contains no native exception or key content. Retry after unlock. The background can read credentials after first unlock and keeps handling read failures after a restart and before first unlock. This accessibility setting applies only on iOS.

Before rendering, the reader removes every meta http-equiv and every non-stylesheet link, which blocks auto-refresh and resource prefetch. iOS hands only top-level links with navigationType=click to the system. On Android, the user must first confirm the real domain and the full URL. The remote image CSP allows only HTTPS. The reader's CSP adds `form-action 'none'` and `base-uri 'none'` to the desktop resource limits, and the reader removes form subtrees before rendering, so an Android POST cannot bypass the navigation callback. The WebView always refuses navigation. Only http, https and mailto links that pass the tap or confirmation flow above and contain no URL username or password go to the system browser or mail app. The OAuth callback routes to the account screen through `+native-intent.tsx`, and AuthSession still listens for and validates code and state.
