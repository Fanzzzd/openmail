# Sync and send results

Migration 39 clears the Outlook full and Inbox delta cursors so that sync fetches `inferenceClassification`. The next sync pulls the mail and message text inside the sync window once more. The cache outside the window stays, but its classification is not filled in automatically. An unknown classification is treated as Focused for now, and the user can change the classification directly.

When UIDNEXT goes backwards while UIDVALIDITY stays the same, the old UIDs can no longer be trusted. core first invalidates remote draft references, turns the old queued operations into `reconcile` with an invalid provider ID, and revokes old undo records and pending approval proposals. When UID identity becomes invalid, core quarantines and keeps the whole old cache and verifies it by Message-ID. A rediscovered message gets a new local generation ID and does not reuse the old handle. In this case core does not remap old UIDs automatically. The reading view clears the old content when the message query returns not found. IMAP full sync and ordinary Inbox polling pull first and push second. They are mutually exclusive with the push queue per account, so operations on other accounts do not wait for the pull to finish. When UIDVALIDITY changes, core still remaps by Message-ID, and each old row is used at most once per pull. The mobile OS background task only pulls incrementally and does not push the queue. Implementation: [store.ts](../packages/core/src/store/store.ts), [mailbox-live.ts](../packages/core/src/mailbox/mailbox-live.ts), [Node IMAP](../packages/core/src/platform/node/imap/adapter.ts) and [mobile IMAP](../packages/core/src/platform/react-native/imap.ts).

After a folder becomes invalid, local changes that have not synced yet are dropped. This includes labels, read state, stars, snoozes and queued remote draft deletions. The related operations keep only cleanup records with invalid IDs, and orphaned snooze rows are deleted. After SELECT, push checks the stored UIDVALIDITY and the lower bound of UIDNEXT. If it finds a rollback, it returns a permanent error and waits for a resync.

When UIDVALIDITY has changed but the next pull has not remapped yet, desktop push searches under the new UIDVALIDITY for the Message-ID recorded at queue time. If it finds exactly one message, it returns the new ID in `ProviderError.remap`, and the queue renames the operation and retries at once. If it finds none, it returns a retryable ProviderError and waits for the pull to remap. Mobile push returns a retryable error directly. `fetchMessage` also returns a retryable error for an old ID, so reconcile no longer deletes the cached row for that reason. Old mail outside the 90-day rebuild window therefore stays and is renamed by Message-ID the first time the user acts on it. `remapProviderIds` makes renamed queued operations retryable immediately. Regression: [imap-uidvalidity-push.test.ts](../packages/core/src/platform/node/imap-uidvalidity-push.test.ts).

## IMAP copy, move and drafts

On both platforms, a move first COPYs, confirms the target identity, and then deletes the source copy. With UIDPLUS, core expunges the source UID directly. Without it, core only sets `\Deleted` and does not run a global EXPUNGE. Sync, history pulls and server search on both platforms treat `\Deleted` mail as absent, so the source folder copy does not come back. Without UIDPLUS, the original stays on the server until another client or the server removes it. Permanent deletion still requires UIDPLUS. If another client clears `\Deleted`, the old UID reappears only after a full window rescan following a cursor reset. Without CONDSTORE, flags for known UIDs get a full scan at most once every ten minutes. After openmail pushes `\Seen` or `\Flagged` successfully, core updates the flag record for that UID in both the full cursor and the Inbox cursor. Otherwise, if another device later changes the flag back, the server state would equal the old record and no flag change would appear.

Before COPY, core persists `issued` progress keyed by queued operation, source provider ID and target folder. After a success reply it records `accepted`. The first attempt copies normally, even if the target already holds the same Message-ID. Only a retry checks the target using the progress record, and if it finds the message it only redoes the source deletion. An explicit rejection clears the matching progress. A lost reply keeps it. If neither source nor target exists and there is no progress, core returns PermanentError, ends the operation and reconciles. If there is progress but the result is unconfirmed, core keeps waiting. Batch operations record progress per message, and one message's progress never counts for another.

When COPYUID is missing, core looks up the target UID by Message-ID. If the message has a Message-ID but the UID is unconfirmed, core keeps the source copy and the queue entry. If it has no Message-ID and COPY is confirmed, core finishes the source deletion, queues a reconcile, and pauses later operations on the old ID for this round; the next pull restores the cache. Before a retry, core checks the source message identity, comparing with angle brackets and whitespace removed. If the identity does not match, core stops the operation and failed_ops shows "Message identity changed". Online, reconcile restores the current server message. Offline, core keeps the cache and queues a reconcile. It does not copy or delete a message that reuses the UID. IMAP copy in `mailbox.organize.perform` goes straight to the queue and skips the move-target check. A non-IMAP copy returns InvalidInput before anything is queued, and a mixed-account selection does not run a partial copy. Mobile special folders also match on the last path segment, for example `INBOX.Sent`. A CREATE that returns `NO [ALREADYEXISTS]` counts as already existing.

When Node IMAP flag, copy or delete calls return false, core retries them as ProviderError. When PERMANENTFLAGS forbids a needed flag, the operation fails permanently. Before a draft APPEND, core records the Message-ID. A retry first looks for an already appended copy, so it does not append twice. Edits or manual retries during backoff keep this identity and progress. If the content has changed, core replaces the recovered copy, so only the newest visible copy remains. If the recovered UID equals the old reference, core does not delete that copy. When the user discards a draft or keeps only the local copy, core queues cleanup of unconfirmed copies by the recorded Message-ID. When the draft switches accounts, the cleanup runs on the original account and the old identity is not used for the new account. If the new draft UID is unknown, core keeps the old copy and fails. If the new link is settled but cleanup of the old copy fails, core queues a deleteDraft to retry the cleanup.

Implementation: [Node IMAP](../packages/core/src/platform/node/imap/adapter.ts), [mobile IMAP](../packages/core/src/platform/react-native/imap.ts) and [Store](../packages/core/src/store/store.ts). Regression entry points are in [testing](testing.md#outbound-operations-and-sending-regressions).

## Outbound operation queue

After a failure, `pending_ops` stores retry_at. The first wait is five seconds, then exponential backoff up to one hour, and each wait starts up to 20% early at random. A flush skips operations that are not due yet and does not jump past an earlier failed operation on the same message. Offline, transport failures, 429/deferred and 5xx are never dropped by retry count. PermanentError ends the operation at once. An ordinary operation expires when a push fails again after it has been queued for seven days. reconcile stays as long as the account is unreachable. AuthError pauses the account, marks it as needing sign-in again and releases the claim without adding to the failure count. A read-only session does not push the queue.

A claim lasts two minutes, and a long push renews it every thirty seconds. Each claim has its own token, and core checks the token when settling the operation and when writing the remote draft link. A failed renewal or local remap affects only the current operation; unrelated operations and pulls continue. An old process cannot settle an operation claimed by a new process. core cleans up a separate draft copy created by a late upload, and queues a delete if the cleanup fails. A copy the current draft already references stays.

Migration 36 adds retry time, claim token, Message-ID, copy progress and draft APPEND identity. Existing queued operations get their Message-ID filled from the cache. Non-reconcile operations that end during a push, and send warnings, go into failed_ops. Desktop and mobile show the count by category, with the operation, subject, sender and reason, until the user dismisses the notice. Graph write responses 400, 404, 409, 413, 415, 422 and `403 ErrorAccessDenied` are permanent errors. The UI shows a short reason, not the Graph JSON.

Implementation: [mailbox-live.ts](../packages/core/src/mailbox/mailbox-live.ts), [store.ts](../packages/core/src/store/store.ts), [db/migrations.ts](../packages/core/src/db/migrations.ts) and [Outlook](../packages/core/src/providers/outlook/outlook.ts).

## Send results

The total retry wait for each HTTP request is at most 60 seconds. When Graph returns Retry-After with a 429 or 5xx, core updates the account's pull deadline at once. Later JSON, MIME and read-only batch requests all check that deadline, so other requests are blocked without waiting for the current request to use up its retries. Outlook send, reply draft preparation and send confirmation use their own request permit and do not queue behind rate-limited pulls. When an IMAP operation is interrupted, core closes the connection and removes it from the push pool. On mobile, commands on one connection run serially.

Gmail and Graph send POSTs are not retried automatically. The Message-ID uses a random local part and the sender's domain, and no custom tracking header is sent. After a dropped connection or a 5xx, core queries Sent at increasing intervals for about 30 seconds. It reports success only if it finds the copy. If it still cannot tell, it returns `SendUncertain`, keeps the draft and persists a resend guard locally. Sending the same draft again requires the user to confirm in the app that they checked Sent. The guard survives a restart.

The official Gmail docs require RFC 2822 MIME and support `rfc822msgid` search, but do not promise to keep a Message-ID set by the client. core first searches for the full ID. If that returns nothing, it searches Sent candidates from one minute before to two minutes after submission, reads the Message-ID metadata and checks the random local part. It does not rely on undocumented partial ID search. If the server also rewrites the local part, the send cannot be confirmed and the resend guard stays. Automated tests cover a kept ID, a rewritten domain, a delayed copy and a missing copy. No probe mail was sent from a real account. See [sending mail](https://developers.google.com/workspace/gmail/api/guides/sending), [messages list query](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list) and [Gmail search operators](https://support.google.com/mail/answer/7190).

Graph queries Sent by `internetMessageId`. When the result of creating a reply draft at send time is uncertain, core queries Drafts only by the ID set at submission and cleans up matching orphaned drafts. It does not delete candidates that match only by conversation or creation time. A failed draft preparation also cleans up a draft whose ID was obtained. A successful send never deletes the Sent copy. See [create reply draft](https://learn.microsoft.com/en-us/graph/api/message-createreply?view=graph-rest-1.0) and [update draft Message-ID](https://learn.microsoft.com/en-us/graph/api/message-update?view=graph-rest-1.0).

When IMAP SMTP loses the reply after the DATA terminator was sent, core queries Sent by Message-ID. If it cannot confirm, it returns SendUncertain and keeps the draft and the resend guard. A connection refusal, timeout or greeting failure before DATA is a definite failure. A 5xx rejection is also a definite failure, and an authentication error still prompts for sign-in. If saving the Sent copy fails after SMTP accepted the message, core reconnects and retries APPEND once. If that fails too, the UI shows a missing-copy notice, and core does not send the mail again.

When Node SMTP rejects some recipients, core lists the rejected addresses, keeps the original draft and turns on the resend guard. "Resend to rejected recipients only" in the notice creates a new draft that keeps only the rejected To/Cc/Bcc, along with the message text and attachments. It does not send automatically and does not change the original draft.

Send confirmation is implemented in [provider-send.ts](../packages/core/src/providers/provider-send.ts), [Node IMAP](../packages/core/src/platform/node/imap/adapter.ts) and [mobile IMAP](../packages/core/src/platform/react-native/imap.ts). Mailbox exposes failure notices through listFailedOps, acknowledgeFailedOps and prepareRejectedResend.

## Drafts and other writes

POSTs that create drafts, attachments, rules, labels/folders and meeting responses are retried automatically only on 429. A 5xx or a lost response is not replayed. Gmail modify-labels, trash and untrash POSTs can be replayed. Calendar `PATCH sendUpdates=all` is not replayed, so notifications are not sent twice.

Before creating a draft, core stores the client Message-ID, the attempt time and the count of query misses in the existing prefs. DNS or connection failures where the client can confirm the request never left can be retried directly. Any other unconfirmed create first looks for the draft with Gmail `in:drafts rfc822msgid:` or Graph `internetMessageId`. core creates the draft again only after at least three query misses and two minutes since the attempt. The attempt time only controls the retry interval. It is not used to identify a server draft.

Outlook resumes editing or cleans up an unconfirmed copy only when the exact client Message-ID and `isDraft=true` prove ownership inside that account's Drafts folder. With several hits, or with more pages left, the state stays uncertain. An exact hit is not limited by creation time, modification time or conversationId. Conversation, close timing, an apparently unedited body, an unlinked local draft or a single candidate cannot prove ownership, and core does not guess. When Graph replaces the client Message-ID in an uncertain createReply, recovery treats it as a miss and creates the draft again once the retry conditions are met, and cleanup keeps the unknown copy. So an empty duplicate reply draft can stay in Drafts until the user deletes it. We prefer leaving a copy to overwriting or deleting content another client wrote. Reply all and forward follow the same rule.

When the user discards or sends a local draft and the creation log still says attempted, core first queues cleanup of the server draft by the log's Message-ID in the same transaction, then clears the log. Writes to the creation log and the remote reference check the current claim token, so an old worker does not overwrite a new owner. As soon as core has the new ID from the create response, it persists the remote reference. A later PATCH or attachment failure still returns that ID along with the sync error. After creating a Graph reply, reply all or forward, core PATCHes the client Message-ID. An ordinary Outlook update rebuilds the draft only when the first PATCH returns 404. A 404 during the attachment stage does not rebuild. If deleting the old draft after a forward replacement fails, the durable `deleteDraft` queue handles it.

When the result of an Outlook attachment upload is uncertain, core reads every attachment page and checks file name, content bytes and Content-ID. A resumed create adds only the missing attachments. When a server draft is opened, core stores changeKey and lastModifiedDateTime right away. The remote version keeps only changeKey and the server modification time, and core never fills them from the local clock. Before an update, core GETs and compares. It saves a separate local version and reports a conflict only if the version differs and the server modification time is later than the last write. After a partial failure following PATCH, core rereads the version. If the read fails, core clears the old changeKey so this write is not mistaken for a change by another client. The Graph [message update docs](https://learn.microsoft.com/en-us/graph/api/message-update?view=graph-rest-1.0) do not promise If-Match, so the comparison still has a race between GET and PATCH.

The response to a draft update can be lost. The server has then changed the version, but the client never got the new changeKey or new message ID. Before sending the PATCH (Outlook) or PUT (Gmail), core stores the SHA-256 of this write's content in `DraftRemote.writeNonce`, and the write carries it too. Outlook uses the extended property `OpenmailDraftWrite`, Gmail the header `X-Openmail-Draft-Write`. On the next save, if the version comparison says conflict, the adapter reads the remote nonce once more. If it equals the fingerprint of this content or the stored `writeNonce`, the change was our own, and core updates in place without saving a separate draft or reporting a conflict. `setDraftRemote`, which confirms a successful save, clears `writeNonce`. Regressions: [outlook-draft-lost-response.test.ts](../packages/core/src/providers/outlook/outlook-draft-lost-response.test.ts) and [gmail-draft-lost-response.test.ts](../packages/core/src/providers/gmail/gmail-draft-lost-response.test.ts).

The same local draft can be open in the Mac compose window and in the remote web page on a phone at the same time. Migration 51 adds `revision` and `editor` to `drafts`. Each local save increments revision and records the editor session that saved it. An editor's save carries `DraftInput.expectedRevision` (the revision it loaded, 0 for a new draft) and its own `editor`. If the last save came from another editor, the phone or an agent, and the revision has changed, core rejects the save and returns `DraftConflict`. Queued saves from the same editor do not conflict with each other. When the compose window gets `DraftConflict`, it reloads the newer version, explains this in a one-line notice and offers "Restore my version", which saves the user's text on top of the newer revision. Saves without `expectedRevision` (CLI, MCP) write directly as before. Regressions: [concurrent-draft.test.ts](../packages/core/src/mailbox/concurrent-draft.test.ts) and [draft-conflict.test.ts](../apps/desktop/src/renderer/src/features/compose/hooks/draft-conflict.test.ts).

### Outlook large attachments

Rules checked on 2026-10-07:

- The [Graph Outlook upload guide](https://learn.microsoft.com/en-us/graph/outlook-large-attachments) and [createUploadSession](https://learn.microsoft.com/en-us/graph/api/attachment-createuploadsession?view=graph-rest-1.0) say that files under 3 MB are added directly and files of 3–150 MB use an upload session that PUTs byte ranges in order. The upload URL already carries authorization, so PUT and resume queries send no Authorization header and do not rewrite the URL. The last chunk returns 201. Ordinary progress returns 200 and nextExpectedRanges.
- The Outlook docs recommend chunks under 4 MB. [Multiples of 320 KiB and under 60 MiB](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession?view=graph-rest-1.0#upload-bytes-to-the-upload-session) is a OneDrive rule, so 60 MiB cannot serve as the Outlook chunk limit. core uses 9 × 320 KiB, or 2,949,120 bytes, for every chunk. The last chunk can be shorter.
- The [Graph limit for ordinary write requests](https://learn.microsoft.com/en-us/graph/use-the-api#http-methods) is 4 MB, including JSON and Base64 overhead. A single small file is still uploaded directly. When several small files together exceed the request limit, core adds them to the draft one by one. If the message text and headers alone exceed the limit, core still reports an error.
- The [Outlook.com note](https://support.microsoft.com/en-us/support/known-issues/unable-to-attach-files-in-outlook-com) sets a 25 MB total message limit that includes message text, inline files and attachments. The [sending limits page](https://support.microsoft.com/en-us/outlook/sending-limits-in-outlook-com) also lists a 25 MB attachment limit. The default 35 MB in the Graph docs applies to Exchange Online mailboxes where an admin can configure it, not to the personal accounts that are the only ones supported now. The preflight counts Base64, line breaks, message text and a 256 KiB header margin. The server still makes the final size decision.
- The [attachment resource docs](https://learn.microsoft.com/en-us/graph/api/resources/attachment?view=graph-rest-1.0) limit itemAttachment to under 3 MB. Upload sessions support only file. core rejects message/rfc822 of 3 MB or more explicitly. Sending a small EML keeps the original MIME path, and the full request must still be under 4 MB.

Sending a large file first creates a separate send draft. In prefs under `send-prepare:<local draft ID>`, core records a random Message-ID and the creating/preparing/sending stage. It stores neither the upload URL nor attachment bytes. After a lost create response or an interrupted preparation, core accepts only a single exact Message-ID hit in Drafts with no further pages. On a miss, it first runs at most three bounded queries against Sent. A failed query does not rebuild. A copy already sent from the web counts as delivered. Otherwise core rebuilds the draft with the same Message-ID. If Graph reply creation replaces the Message-ID and is interrupted before PATCH, an unknown empty draft can remain, but core never sends those copies automatically. core persists the sending stage before submission. An ordinary retry only queries Sent and does not submit again. When the user explicitly confirms Send again, both direct send and the undo queue, in one transaction, first queue draft cleanup by the old Message-ID, then clear the old preparation record and resend under a new send intent. An explicit send rejection can return to preparing. An upload failure keeps the identified draft for a retry. A direct call without a durable log deletes only the temporary draft that matches the exact identity when it fails. Discarding the local draft queues cleanup by Message-ID, and a Sent copy does not match the Drafts cleanup conditions.

Each upload continues from nextExpectedRanges. When a PUT fails, core first queries the session status. If the final response is lost, core checks the attached content chunk by chunk so it does not create a duplicate attachment. Each chunk's timeout assumes at least 20 KiB/s plus a 30-second margin. core does not skip a PUT based on the local clock or the server expiry time. It rebuilds the session only when a request returns 404/410 or a session-expired error, at most twice. An abandoned upload DELETEs the upload URL without an Authorization header. Resume queries GET the upload URL and accept both nextExpectedRanges and NextExpectedRanges, following the [Microsoft SDK implementation](https://github.com/microsoftgraph/msgraph-sdk-javascript/blob/dev/src/tasks/LargeFileUploadTask.ts). When the whole transfer fails, the existing draft and send error paths handle it. The undo window, outbox claims and pending-op rules do not change. Message text counts both before queuing and at send time. Fixed size errors and upload errors reach the UI through an exact RPC allowlist and Lingui. Arbitrary error text from the provider is still filtered.

An upload decodes only the current chunk. The compose model holds the existing Base64 source, and core no longer builds the full binary or a large attachment JSON. It normalizes whitespace once before upload. Recovery lists only attachment metadata, filters by name, type and isInline/Content-ID, and then compares bytes as a stream. The Graph size is the stored size and cannot identify content: in the official example, an upload of 3,483,322 bytes returns 3,640,066 bytes on GET. Draft saving keeps the creation log and remote version, and unchanged attachments are not uploaded. The adapter caches verified attachment IDs and chunk content fingerprints. A PATCH by the adapter itself that changes only the message text keeps the cache. A remote version change or a restart triggers verification again. Regression: [outlook-upload.test.ts](../packages/core/src/providers/outlook/outlook-upload.test.ts). It covers an inflated size, a lost final PUT response, recovery at each stage, confirmed resend, slow uploads and clock skew, 10 MB chunking, the 100 MB memory bound, and saving after a server draft is reopened. All Graph tests use a fake HTTP service and do not call the real Microsoft API.

When the result of creating a rule is uncertain, core rereads and matches conditions, actions and exceptions. A Gmail rule update must first verify the new rule. If it is still unconfirmed, core keeps the recovery record for the original rule and does not restore it or replay the create automatically. A meeting response rereads responseStatus or the user's own attendee status and reports success only when it matches. A label/folder create conflict rereads by full name. Gmail handles both 400 and 409 and reports success only when it finds a user label with the same name. The official Gmail [labels guide](https://developers.google.com/workspace/gmail/api/guides/labels) states that a reserved name conflict can return 400 and does not specify the status code for a duplicate custom name.

Before a Gmail move out of Trash, core verifies the target label. If the modify after untrash fails, core restores Trash. If that restore also fails, core reports that the location needs checking.

## Durable send intents

For the desktop undo window, core persists the message, deadline, owning window and archive-after-send option. The waiting task belongs to the Mailbox Layer. A renderer disconnect does not cancel the send. When the user approves quit, reload, or closing the compose window, core cancels the matching waiting item and keeps the draft. After an unexpected restart, only the desktop main process recovers waiting items. CLI/MCP do not recover or flush these sends. When a desktop intent recovered at startup is more than two minutes past its deadline, core changes it to retryable and shows a failure notice, keeping the draft for the user to resend, so a stale mail does not go out unexpectedly after a quit or crash. A waiting task scheduled by this process always sends when its timer fires and does not check wall-clock expiry. Timers stop during system sleep, so the wall clock may be far past the deadline after the lid opens, but the user did send, and the undo window has passed in the time the user saw. `flushQueuedSends` still checks the deadline when it claims a desktop intent. Undo asks core to cancel the waiting intent. A send that is already claimed cannot be undone. A successful undo interrupts the core waiting task. A finished core waiting task removes itself from the worker table. A window cancels only its own waiting intents. Intents without an owner are handled only by a global quit. The renderer clears pending state by each send's token. While an undo is in flight, it waits for the cancel result and hides the send result only if the cancel succeeded. If the cancel fails, it still shows the actual success or failure. If the server refuses the undo, the renderer clears the toast and the Undo action and keeps the pending state until the send ends. A separate send ID stops an old timer from sending a new intent for the same draft. When the same draft already has a waiting/sending item, a direct send rejects the duplicate.

The outbox rereads waiting, claims it as sending and saves the resend guard in one transaction. The lock covers only the claim and result transactions, so other drafts can be queued or undone while the provider sends. A normal desktop send also saves the guard before calling the provider. core clears the guard only when every recipient was delivered. It keeps the guard only when the adapter returns SendUncertain. Every other error, including a request failure before sending, clears the guard. A partial SMTP rejection uses the guard from the send results section and keeps the failed outbox item. A definite outbox failure is marked retryable, and "Retry send" on mobile opens the kept draft for the user to check. When the result is uncertain or the process exits mid-send, the guard stays and the mail cannot be resent automatically. At startup, core changes interrupted sending items to failed, and the user can queue them again after confirming. Desktop send failures and interruptions show notices through failed_ops, including for recovered tasks and disconnected renderers. All of this state reuses prefs, with no new migration.

## Reset deletion guard

The keep set of a reset covers only the range listed in this round. Outlook initial sync and 410 restarts filter by `receivedDateTime` over the last 90 days and page in descending order. The delta URL has no `$top`. The initial request, nextLink and deltaLink each send `Prefer: IdType="ImmutableId", odata.maxpagesize=50`. Ordinary list endpoints can still use `$top`. Delete candidates use the same start date, and messages outside the window stay. A filtered delta returns at most 5,000 items, so it cannot prove that missing mail was deleted. Every missing item inside the window must be verified. Without a final deltaLink, core keeps the old cursor and lists again next round. The [Graph delta docs](https://learn.microsoft.com/en-us/graph/delta-query-messages) describe the filter, ordering, item limit and continuation links.

Gmail history-404 recovery lists the last 90 days. Recovery paging is not bound by the 2,000-message limit of initial sync, and Reset covers only the same date range. An IMAP UIDVALIDITY rebuild checks only the window from the SINCE date, and takes at most the newest 1,000 messages per folder, so missing items inside the window must be verified too. The flag scan for known UIDs cleans up only IDs it explicitly scanned. A vanished folder and a reused UID are checked against the original folder identity and the Message-ID respectively. The existence of a new UID is never taken as proof that the old message is still there.

Slice 62 removed the deletion count threshold. In Reset, DeleteLabel and RebuildFolder, every delete candidate not in keep first goes into a durable verification queue. Even a single missing message must be verified. core never deletes directly because a listing is marked complete or is empty. The budget, resumed verification and sweep rules of the durable queue are in [stale cache sweep](#stale-cache-sweep). Graph sends at most 20 read-only requests per batch, uses four pull permits and honors Retry-After on inner requests. The send permit stays separate. Gmail reads in minimal batches. IMAP uses UNDELETED UID SEARCH and Message-ID search. core deletes only after confirming the message is gone. If it finds a copy in the same folder, it keeps it. If the message moved to another folder, it updates the owning folder. The `sync-reset` log records only account and folder hashes and counts. Outlook logs a listing only on the first cursor, an identity reset or a 410 restart. An ordinary incremental pull is not logged as a reset, and an empty listing also saves the final deltaLink.

The guard shipped with slice 56. The verification queue persists in the existing prefs, with no new migration. While the local queue is not fully verified, the cache stays. A read-only session allows these existence probes, including Graph batches that contain only GET subrequests. Implementation: [sync-reset.ts](../packages/core/src/sync/sync-reset.ts), [store-sync-reset.ts](../packages/core/src/store/store-sync-reset.ts), [Outlook](../packages/core/src/providers/outlook/outlook.ts), [Gmail](../packages/core/src/providers/gmail/gmail.ts) and [read-only.ts](../packages/core/src/mailbox/read-only.ts). Regressions: [sync-reset.test.ts](../packages/core/src/sync/sync-reset.test.ts) and [sync-reset-imap.test.ts](../packages/core/src/sync/sync-reset-imap.test.ts).

The Node IMAP adapter treats false/undefined from ImapFlow SEARCH as ProviderError and does not turn it into an empty UID set. Initial pull, incremental pull, flag scan, history backfill, server search and existence verification share this rule, so a failed search can never prove that mail disappeared. When a folder is missing from a listing, core first checks STATUS. It confirms the deletion only on an explicit NotFound and a second LIST that still lacks the folder. A failure or a hidden folder keeps the old state. Outlook likewise first GETs the missing folder directly, enters deletion verification only on an explicit 404 and keeps the old cursor for any other result. Implementation: [Node IMAP](../packages/core/src/platform/node/imap/adapter.ts), [Outlook](../packages/core/src/providers/outlook/outlook.ts) and [store.ts](../packages/core/src/store/store.ts). Regressions: [imap.test.ts](../packages/core/src/providers/imap/imap.test.ts) and [sync-reset-imap.test.ts](../packages/core/src/sync/sync-reset-imap.test.ts).

## Resuming after failure

Gmail initial sync first takes the historyId from `/profile` and saves the cursor `initial:<historyId>` before pulling bodies. A retry uses this historyId, lists IDs again, skips stored messages and does not refetch with `format=full`. When the sync finishes, the cursor becomes the original historyId, and later history covers changes between the two attempts. A rate-limit ProviderError (429, or Gmail 403 with rateLimitExceeded, userRateLimitExceeded or totalQueryCostPerMinutePerUser) carries `reason: "quota"`. Full sync retries it twice, waiting 30 s and 60 s. When the server sends Retry-After, core waits that long, and if it exceeds two minutes, the next scheduled sync takes over. Network errors and 5xx still wait 5 s and 10 s.

Outlook full sync saves a cursor with a `__partial` marker after each finished folder. Finished folders get the new delta link, and the rest keep the old link. Before saving, core puts removals it has seen whose target was not listed into the verification queue. A restarted folder first issues DeleteLabel, and its keep set leaves out IDs already queued so they are not removed from the queue. On retry, folders without a link in the marked cursor are treated as restarts. Old-format cursors (without the immutable ID marker) must Reset after all folders and are saved only at the end. When a pull fails mid-sync, core first writes the changes received before the failure and then reports the failure, so the checkpoint in the batch buffer is not lost.

## Stale cache sweep

After a full sync, the stale sweep runs at most once per account per hour. The sweep time and page position persist in prefs and carry over a restart. It scans only folders where the server count is available and `local.total > server.total`. core first gets summary counts for all folders, then uses whatever is left of the account's ten-second budget for optional rechecks. Rechecks apply only to Gmail categories/Drafts and Outlook Drafts, and each takes at most one second. The plain Inbox never enumerates IDs. Gmail pages through IDs only, with explicit includeSpamTrash=true, at most two pages each for total and unread. When the summary total exceeds the 1,000 messages two pages can count, core skips the recheck. Once the total listing hits that cap, core does not list unread. Graph uses `$count=true` on the folder's messages and queries total and unread separately. When a recheck hits the cap, times out or fails, core keeps the summary counts it already has and the available state, and can still sweep old rows. Only a failed raw summary read marks the provider unavailable. A folder that no longer has excess after the recheck does not go to per-item verification. Excess unread alone does not trigger a sweep, because Graph and IMAP location verification does not read current flags.

The sweep verifies at most 500 IDs per account per round, with its own budget. Reset and Outlook conflict verification still share the durable queue budget of 500 IDs per sync round across all accounts. The sweep skips IDs that are queued or already verified this round, so it does not use the reset budget or repeat requests. Failed and unverified rows stay. The sweep position rotates and verification resumes the next time the hourly limit allows. For each sweep row it has verified explicitly, core stores in the same prefs state the first 16 characters of a combined hash of provider ID, Message-ID and labels, and skips unchanged rows for 24 hours. A label or identity change triggers verification again. This record does not limit the reset queue. `incomplete` counts only candidates without a definite result this round. A row confirmed to be still in its original folder counts as done. Network requests follow the provider's locks and retry rules. When a batch runs out of retries, core stops the remaining batches and does not bypass Retry-After.

The count difference only bounds the candidates. Cleanup reuses the server verification path above. Verification results are layered over pending operations, so local changes that have not synced stay. Gmail drafts.list reads one page of up to 500 only when there are uncached orphaned remote draft candidates. Listed IDs prove existence. IDs that are not listed still need per-item verification. When every candidate is cached, core does not make that request.

Drafts counts an orphaned draft only if it has a `remote_message_id`, `local_only=0`, `sync_error IS NULL` and no matching message row, deduplicated by remote message ID. Sweep candidates use the same rule. Drafts that are not uploaded yet, local-only drafts and drafts with a sync failure do not count as orphaned remote rows. 404 cleanup still protects drafts with a pending saveDraft and does not delete edits that are not uploaded.

When Outlook reports an update and a removal for the same ID in one round, and the update folder overlaps the removal folder, core saves the ID to the durable verification queue first and the cursor second. The pull does not verify inline. Later verification checks the current location under the shared budget. Rate limits, permission errors and IDs without a definite answer stay queued and are verified in later syncs. This covers a message moved from a folder processed later into Inbox, where the old folder's update overwrote the new location. A removal that no folder lists also goes into the verification queue first and is not deleted directly. The `receivedDateTime` start of a folder delta is fixed when the cursor is created, so when a February message moves into a folder created in June, the new folder's delta does not list it. Verification reads `parentFolderId` and moves it to the new folder. Verification confirms truly deleted mail as gone and then deletes it, at the cost of one extra read-only batch request per 20 deletions. Inbox polling does not handle removals and does not GET custom folders one by one. The Inbox cursor keeps only the Inbox delta link, and full sync still decides folder deletions.

Implementation: [sync-reset.ts](../packages/core/src/sync/sync-reset.ts), [store-sync-reset.ts](../packages/core/src/store/store-sync-reset.ts), [Outlook](../packages/core/src/providers/outlook/outlook.ts) and [store-sync-health.ts](../packages/core/src/store/store-sync-health.ts). Regressions: [sync-stale.test.ts](../packages/core/src/sync/sync-stale.test.ts), [sync-reset.test.ts](../packages/core/src/sync/sync-reset.test.ts) and [outlook-sync-health.test.ts](../packages/core/src/providers/outlook/outlook-sync-health.test.ts).

## Header backfill for old cached mail

Slice 66 backfills old rows where `rfc_message_id IS NULL OR headers_json IS NULL`. It runs after each successful full pull per account, and in separate background maintenance when automatic sync is on. It goes in descending order of mail date and local ID, 20 rows per batch, at most 500 rows per account per round. A separate cursor and completion time live in `prefs` under `sync-headers:<account>`. Each batch's writes commit together with the cursor, so the work resumes after a restart. Once complete, it stops making requests. Separate maintenance picks one unfinished account every ten seconds and does not wait for Graph delta rebuilds. It shares the account backfill lock with full sync, IMAP must also take the pull lock, and it skips the account when busy. No new migration.

Gmail GETs metadata serially under the shared account request permit and uses `metadataHeaders` to name the cached fields for identity, reference chain, delivery, mailing list, security and so on. The set is in [header-backfill.ts](../packages/core/src/sync/header-backfill.ts). Graph `$batch` sends at most 20 GETs per batch with explicit `$select=internetMessageId,internetMessageHeaders`, at most 25 batches per round, and keeps ImmutableId, the pull permit and Retry-After on inner requests. When a successful Graph response omits headers or returns null, core caches `[]`, advances the cursor and keeps any Message-ID returned. A row without a Message-ID is also scanned only once. The retry deadline after a failed request persists in the backfill state and carries over a restart. Graph pull requests share the account rate-limit deadline, and the send permit stays separate. The [Graph headers docs](https://learn.microsoft.com/en-us/graph/api/message-get?view=graph-rest-1.0#example-2-get-internet-message-headers) require `$select` to get headers. Desktop and mobile IMAP group by folder, check UIDVALIDITY and the lower bound of known UIDs, and only run a read-only open and `UID FETCH BODY.PEEK[HEADER.FIELDS (...)]`. They keep repeated fields and unfold folded lines. A normal mobile pull also stores headers, so no new header-less cache rows appear.

The backfill only UPDATEs the two missing fields. It does not overwrite existing values and does not change rowid, labels, flags, threads or bodies. FTS, the word index and the message-derived triggers do not watch these two columns. A read-only session allows remote reads and these cache writes. A 404, 410, missing UID or unsafe IMAP identity is only skipped and left to ordinary sync and existence verification. No mail is deleted. When earlier existence verification is postponed, core skips the backfill at the end of sync, and separate maintenance also honors the account's Retry-After. When a backfill request fails, a rate limit exceeds the wait budget, or a reply is missing, core stops this round and keeps the cursor of the unfinished batch. A scan can also complete when a header has no Message-ID. Automatic sync maintenance only handles accounts that already have a sync cache, and the mobile OS incremental background task does not run it.

Implementation: [header-backfill.ts](../packages/core/src/sync/header-backfill.ts), [store-header-backfill.ts](../packages/core/src/store/store-header-backfill.ts) and [mailbox-live.ts](../packages/core/src/mailbox/mailbox-live.ts). Regressions cover reads, repeated and folded fields, namespace protection, rate limits and read-only rules for all four adapters. The [persistence test](../packages/core/src/platform/node/header-backfill.test.ts) covers the 500-row budget per provider, resuming after closing and reopening the database, stopping after completion, account isolation, keeping labels and flags, and no extra FTS writes. A fake Graph checks that 3,840 rows finish in eight rounds, including missing headers, missing IDs, existing IDs, retry deadlines and delta blocking.

`logSyncReset` records sync reset counts as Info. The desktop log bridge records each recognized `sync-reset` and `provider-failure` event once and no longer emits an extra `runtime-warning` for them. Real runtime warnings and errors store only a fixed reason code, for example `header-backfill-failed`, `history-backfill-failed` or `sync-failed`. Unknown sources are recorded as `unclassified`. No error text, mail, paths or credentials are logged.

Root-cause evidence and the decision are in the [sync reset ADR](adr/sync-reset-verification.md).

## Sync health check

On desktop, choose an account in Settings → Accounts, click Check sync health, then export the report with Copy redacted report. From the CLI, after a build, run:

```sh
node packages/cli/dist/cli.js health --json
OPENMAIL_READ_ONLY=1 node packages/cli/dist/cli.js health --account 'gmail:me@example.com' --json
```

Omit `--account` to check all accounts. `mailbox.sync.syncHealth` requests Gmail label counts, Graph folder counts or IMAP STATUS. When a summary count is lower than the local count, it rechecks with a read-only query of the message set. It does not read message text and does not modify the provider. It has a network budget of about ten seconds and at most four concurrent requests. A failed folder keeps the local count and is marked provider unavailable. The smoke test outputs the same report. See [testing](testing.md#desktop-production-build-smoke-test) for how to run it.

| Report field                     | Meaning                                                                                                                                                                                                                                         |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `local`, `server`                | Total, unread and, where available, conversation counts. The verdict compares total and unread mail, not conversations                                                                                                                          |
| `bodyCacheWindowDays`            | Days of message text kept. `null` means everything is kept. Headers do not expire because of this                                                                                                                                               |
| `headerWindow`                   | The initial header range while history backfill is unfinished: Gmail 90 days / at most 2000 messages, IMAP 90 days / at most 1000 per folder, Outlook with a `__windowDays="90"` cursor 90 days / at most 5000. Old cursors have no window mark |
| `cursorAgeMs`                    | Milliseconds since the last sync when a cursor exists. `null` means no usable cursor age                                                                                                                                                        |
| `pendingOps`                     | Number of operations waiting to push. Offline local changes can cause count differences                                                                                                                                                         |
| `accountDomainHash`, `checkedAt` | SHA-256 of the account's mail domain and the check time. The hash is not anonymization                                                                                                                                                          |

For Gmail and Outlook Drafts, the local total and conversation count also include rows that meet the [orphaned remote draft rule](#stale-cache-sweep) above, deduplicated by remote message ID. The unread count still comes only from messages.

The difference of 40 local versus about 22 on the server in Outlook Drafts has no real server identity samples yet, so the count alone cannot confirm that Graph failed to report `@removed`. The current code confirms this much: a local message is removed only after an explicit delete event or existence verification. A draft deleted on another device while this one was offline stays in the cache for a while if the incremental sync did not report the deletion. The 90-day window and the 410 relisting do not cover all historical drafts. The stale sweep after a full sync runs hourly with at most 500 items per round, and failed, rate-limited and unverified items stay. So messages that were deleted but not verified yet, and remote drafts not mirrored into messages, can both make local.total exceed the server count. Count rechecks and per-item cleanup already have regressions. This round found no evidence to change delta behavior.

When Outlook Drafts still has excess after the recheck, the health report attaches `diagnostic.code = "OUTLOOK_DRAFT_COUNT_EXCESS"`. `cachedTotal` and `unmirroredDraftTotal` split the two count sources. core takes at most 50 candidates by providerId and runs read-only location/existence verification for at most one second within what is left of the ten-second budget. It reports `sampled`, `gone`, `outsideDrafts`, `presentInDrafts` and `unverified`. These are sample counts, not counts for the whole folder. gone proves the current identity no longer exists. outsideDrafts proves the cached folder ownership is stale. Neither alone proves that delta missed a removal. The next investigation should combine cursor age, last sync time and incremental events. Timeouts and missing responses count as unverified and are not evidence of deletion.

The diagnostic outputs only a fixed code and numbers, and the redacted export keeps it. It does not read message text and does not change the cache, drafts or the operation queue. The stale sweep in a normal full sync verifies its own candidates directly and does not repeat the diagnostic sample. Regression: [sync-health.test.ts](../packages/core/src/sync/sync-health.test.ts).

Read the verdicts as follows:

- Match: total and unread are equal. This does not prove that message identity, flags or content match.
- Fewer local, sync window: the total is below the provider's and the initial header range still applies, so the mail may only be waiting for backfill. For IMAP, if the local count is below the number of UIDs the cursor already tracks, it is still judged missing.
- Fewer local, missing: no window explains it, or totals are equal but unread is lower.
- More local, stale: total or unread exceeds the provider's. A full sync can trigger the stale cache sweep above. The health check itself does not clean up, and a count difference does not prove that any ID was deleted.
- Provider unavailable: the request failed or timed out. This says nothing about local cache corruption.

CLI, desktop copy and smoke export pass through `redactSyncHealth`, which changes custom labels/folders to `folder:N` and keeps only counts, fixed states, times and the domain hash. The report contains no subjects, message text or tokens. Implementation: [sync-health.ts](../packages/core/src/sync/sync-health.ts), [store-sync-health.ts](../packages/core/src/store/store-sync-health.ts), [CLI](../packages/cli/src/cli.ts) and the [desktop UI](../apps/desktop/src/renderer/src/features/settings/sections/SyncHealth.tsx). Regression: [sync-health.test.ts](../packages/core/src/sync/sync-health.test.ts).

## Offline and sync recovery

Gmail/Outlook background pulls, counts, verification and maintenance share a per-account offline backoff. Only non-deferred failures with an explicit status 0 count toward it. Transport failures wait exponentially from five seconds up to five minutes. During the wait, core does not refresh tokens or make background requests, and a deferral does not write provider-failure. Sending, opening a body and downloading attachments bypass the offline wait, and a success resets the failure count. The manual Sync RPC first calls the portable `mailbox.sync.resetConnectivity`. A failed send submission still queries Sent through the existing send confirmation flow, and the offline wait does not block submission or confirmation. System wake, renderer online and mobile AppState active events clear the offline wait and the Inbox polling wait and resume sync at once. Mobile does not install NetInfo. It uses addNetworkStateListener from the existing expo-network for foreground network recovery. A server Retry-After is stored separately, and these events cannot clear it.

When a Gmail/Graph request gets no response headers within 60 seconds, or the response body gets no new data for 60 seconds, core treats it as a status 0 transport failure. Each 20 KiB of request body adds 1 second of upload time to the header timeout. A send then goes through exact Message-ID confirmation in Sent. Token refresh has a 60-second limit, and a timeout does not mark the account as needing sign-in again.

resetConnectivity makes queued operations that failed while offline due at once. Backoff for 429/5xx does not change. It also makes a waiting IDLE reconnect at once. Migration 42 records offline failures in retry_offline. The desktop main process reads `net.isOnline()` every five seconds and calls resetConnectivity and sync when it comes back online. Regression: [network-failures.test.ts](../packages/core/src/providers/network-failures.test.ts).

A provider defect during sync returns fixed failure text and lets later accounts and the next automatic sync round continue. A maintenance exception in runSync also releases the shared wait and the running state. An interruption of a manual sync propagates and releases the state. The automatic loop handles a pure interruption silently and continues with the next round. Closing the scope cancels normally and does not log a crash. The crash diagnostic keeps only the stage (pull/verification/health/headers/maintenance) and the defect/failure category, not the contents of the Cause. The earlier single sync-crashed log lacked these fields, so that particular exception cannot be reconstructed from it. Regressions: `uid-remap.test.ts`, `provider-connectivity.test.ts`, `outlook.test.ts`, `gmail.test.ts`.

The `$select` for Graph search collections does not include internetMessageHeaders. The name/contentType/size/isInline metadata of attachments comes in one pass through `$expand`. Search does not GET attachments or MIME per item. When the provider omits the attachment expansion or a signed container is present, core marks the body as needing a full read and fills it in when the reader opens. An incomplete search result keeps the cached attachment list, and the reader's fill-in writes the full attachment list, so an empty expansion or a raw signed container does not overwrite decoded attachments such as PDFs. Terms with punctuation keep escaped KQL quotes. An ordinary Graph search term uses only one layer, `$search="term"`. Phrases and property queries keep KQL escaping and are not mixed with `$filter` or `$orderby`. Search requests use the read error mapping. Desktop uses Lingui search-specific text and keeps local results. The implementation follows the [Graph search docs](https://learn.microsoft.com/en-us/graph/search-query-parameter), and regressions cover E64KZJ, phrase escaping and search rejection. The redacted logs did not include the Graph response error code or the query. The double quoting of ordinary terms and the internetMessageHeaders selection on collections are removed, and the attachment expansion stays. The original logs alone cannot prove which of these caused that rejection. Search failure diagnostics record operation=search and the Graph error.code from a fixed enum, with unknown values recorded as unknown. They do not record the response message or the query. In a read-only backup of the real database, Gmail CATEGORY_PERSONAL has 22 messages in 21 threads. Outlook Drafts has 40 messages in 37 threads, 38 of them older than 90 days. Both accounts have 0 rows in the drafts table and in pending_ops, so there are no orphaned drafts, local-only drafts or duplicate queue counts. The real provider count requests did not succeed, so these cached rows cannot be excluded on that basis, and the difference cannot be attributed to local SQL either. The conclusion waits for confirmation of the provider totals.

## When to ask for sign-in again

Only a definite answer pauses an account and prompts for sign-in again. core records the reason in `accounts.reauth_reason` (migration 44) and in the diagnostic `reauth` event:

| Trigger                                                                                                                                                                                                                                     | Reason code           |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| The token endpoint returns 400/401 `invalid_grant` or `interaction_required`                                                                                                                                                                | `token_revoked`       |
| Before 2026-10-11: a token issued by the built-in Google client returns `invalid_grant` and was issued at least 6.5 days earlier. The built-in project is published since then, so core no longer produces this reason. Stored records stay | `testing_mode_expiry` |
| The token endpoint returns `consent_required`                                                                                                                                                                                               | `scope_missing`       |
| `invalid_client`, `unauthorized_client`, or the client that issued the token is no longer configured                                                                                                                                        | `client_mismatch`     |
| The keychain has no entry for the account                                                                                                                                                                                                   | `keychain_missing`    |
| IMAP LOGIN is refused after TCP and TLS are established, or SMTP 535                                                                                                                                                                        | `imap_auth_failed`    |
| API 401: clear the cached access token, force one refresh and retry, still 401                                                                                                                                                              | `token_revoked`       |

Everything else is retryable: offline and DNS failures, 5xx, 429, timeouts, a single 401 before the forced refresh, other 4xx from the token endpoint, the RFC 5530 login refusals `UNAVAILABLE`, `INUSE`, `LIMIT` and `SERVERBUG`, and SMTP 454. A 401 on send also refreshes first and then retries, because a 401 means the server did not process the request.

The built-in client's Google app is in Testing, so only that client uses the time check. The publishing state of a user's own client is unknown, and accounts without an issue time cannot be judged, so both are recorded as `token_revoked`.

Keychain read/write failures (locked after sleep, `errSecInteractionNotAllowed`) are retried three times in the Node adapter with exponential backoff starting at 250 ms. When the user cancels or denies the prompt (`errSecUserCanceled`, -128), core does not retry. A final failure returns a ProviderError with `reason: "keychain"` and does not mark the account for sign-in. The sync error shows that the keychain is locked. `@napi-rs/keyring` returns undefined only when the entry does not exist and rejects in every other case.

Token refresh is serial per account. Microsoft rotates refresh tokens: core writes the new token to the keychain first and uses the new access token only after the write. Before writing, core rereads the keychain. If the entry no longer exists, the account was deleted during the refresh, and core does not write. If the write fails, the keychain keeps the old token (the old token of a personal account is still valid), and the new token stays in memory. The next refresh retries the write before using it. When a refresh returns `invalid_grant`, core rereads the keychain once. If CLI or MCP has already switched to a new token, core retries once with it, and marks the account only if nothing changed.

The desktop background checks once 1 minute after launch and then every 6 hours. It refreshes the token once for any OAuth account this process has not refreshed in more than 6 days, including disabled accounts, accounts with sync paused and read-only sessions. It does not pull mail and does not write to the mailbox. Disabled accounts do not sync, so their token refreshes once per app launch, and once every 6 days while the app stays open. A Microsoft personal account's refresh token expires after 90 days of inactivity, and this interval keeps a running app from hitting that limit. Implementation: [reauth.ts](../packages/core/src/providers/reauth.ts), [provider-http.ts](../packages/core/src/providers/provider-http.ts) and [token-keepalive.ts](../packages/core/src/sync/token-keepalive.ts). Regression: [reauth.test.ts](../packages/core/src/providers/reauth.test.ts).
