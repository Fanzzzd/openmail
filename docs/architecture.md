# Architecture

Core owns mail networking, the database, policy and sync. The desktop app, the CLI, the MCP server and the mobile UI call Mailbox. Platform capabilities come from Effect services. Terms are defined in [CONTEXT.md](../CONTEXT.md). Source rules are maintained only in [AGENTS.md](../AGENTS.md).

## Mailbox interface

Mailbox is an Effect `Context.Service`. `NodeMailbox(options)` returns an assembled Layer. The mobile app provides mobile Layers to `MailboxLive`. Callers get Mailbox, then run its Effects or consume its Streams.

Mailbox has eleven groups. A group is a namespace on the one service, typed by an interface in `mailbox/mailbox.ts` and built by its parts. Callers write `mailbox.reading.thread(id)` or `mailbox.organize.perform(command, actor)`. No group exposes the Store. Every member that changes mail writes an audit row inside its part, except draft autosaves: creating and discarding a draft are audited, later saves are not. Message changes from `organize.perform` and from the batch path with undo (`modifyWithUndo`, `snoozeWithUndo`, `undoBatch`) go through `applyMailOp` in `mailbox/mail-change.ts`, which applies, queues and audits each op. `perform` decides with `decide` in `mailbox/policy.ts` for the given Actor, and the batch path runs the same `decide` for the app user. `proposals.decideProposal` runs an approved change as the approving person. Members without an Actor parameter audit as the app user. Members with one check it inline: `unsubscribe`, `importCalendarAttachment` and `createCalendarEvent` accept only the app user, and `respondInvite` accepts any user. Test fakes fill only the groups they use. ADR [0003](adr/0003-mailbox-interface.md) records the decision.

### Policy and changes

`domain/command.ts` defines Command, Actor and Outcome. `decide` in `mailbox/policy.ts` decides by entry point and write permission. User actions take the execute path. Rules execute or propose depending on their permission. Writes from MCP and the built-in assistant need approval, and an agent can never send directly. Tool switches and approval details are maintained only in the [agent guide](agents.md#提议改动).

For an ordinary change, core expands the conversation, applies the local state, records `pending_ops` and `audit_log`, then tries to push to the provider. Rules for retries, claims, failure notices and send results are maintained only in [sync correctness](sync-correctness.md#outbound-operation-queue). When sync writes to the database, it keeps the local result of operations still waiting to push, so a pull does not overwrite offline changes.

The batch path records the inverse state of each message. `mailbox/undo-journal.ts` persists these records, so they survive a restart. Undo checks message state first, so it does not overwrite a later action. Restore records for deleted provider rules are stored separately from mail undo.

### Read-only session

`OPENMAIL_READ_ONLY=1` is read when the Layer is built. Node Providers and the portable Mailbox both wrap the adapter in [read-only.ts](../packages/core/src/mailbox/read-only.ts). It lets through only the listed read and connect methods. Unknown methods and accessors are denied by default. It blocks mail, folders, rules, auto-replies, calendar, draft upload, sending and one-click unsubscribe POSTs. A queue flush skips existing operations, delayed sends do not run, and pending items keep their state.

Local preferences, drafts, read state and proposals can still be saved. The switch does not isolate the database. It does not block network reads, standard Secrets reads or token refresh, and it does not widen OAuth scopes. Wiring and queue entry points are in [Node Layers](../packages/core/src/platform/node/layers.ts) and [mailbox-live.ts](../packages/core/src/mailbox/mailbox-live.ts). Regressions are in [read-only.test.ts](../packages/core/src/mailbox/read-only.test.ts). How to run against a copy of the database is maintained only in [testing](testing.md#desktop-production-build-smoke-test).

### Optional services

[optional-services.ts](../packages/core/src/providers/optional-services.ts) defines the base scopes and the per-service scopes. `scopedAdapter` checks the grant and the local switch before a provider call. Contacts, calendar and provider settings are independent of each other, and a missing permission does not pause mail sync. Only turning contacts off explicitly clears server contacts, groups and photos. Local correspondent addresses stay. Grant compatibility rules are in [store-services.ts](../packages/core/src/store/store-services.ts), and the on/off switch is in [mailbox-services.ts](../packages/core/src/mailbox/mailbox-services.ts). Setup and scope tables are maintained only in [Google](setup-google.md#optional-services) and [Microsoft](setup-microsoft.md#optional-services).

### Providers and Store

`ProviderAdapter.pull` returns `Stream<Change>`. Mailbox consumes message, deletion, label and cursor changes the same way for every provider. Adapters also provide push, send, drafts, attachments, search, contacts and calendar. Gmail and Outlook use portable HTTP. IMAP/SMTP is implemented by the [Node adapter](../packages/core/src/platform/node/imap/adapter.ts) and the [mobile adapter](../packages/core/src/platform/react-native/imap.ts).

[providers/capabilities.ts](../packages/core/src/providers/capabilities.ts) describes what each provider can do as plain data: labels or folders, important, inbox tabs, categories, copy, server rules and their size step, automatic replies, optional services, calendar, send-as, sign-in, the shared IMAP session, web links and server forwards. Core validation, the renderer, the CLI and mobile call `providerCapabilities(account.provider)` and `supportsOp`, so a control the UI shows is one core accepts. Code outside the adapter folders (`providers/gmail/`, `providers/outlook/`, `providers/imap/`), `capabilities.ts` and `platform/` does not compare provider names to decide behaviour. Sync health and sync reset read their per-provider layout (system scopes, the first-sync header window, reset budgets) from [providers/sync-profile.ts](../packages/core/src/providers/sync-profile.ts). A new question about what an account can do becomes a field in the table. Brand names, icons and OAuth client choice still use the name. [provider-names.test.ts](../scripts/repo-checks/src/provider-names.test.ts) counts the remaining comparisons per file and fails when one appears or grows. See [ADR 0002](adr/0002-provider-capabilities.md).

Store uses Effect `SqlClient`. The Node Layer provides `node:sqlite` and optional sqlite-vec. The mobile Layer provides op-sqlite and reports that vectors are unavailable. Both run the same `MIGRATIONS`. Messages are updated through `upsertMessage`, which keeps rowids aligned with the external-content FTS table. Word indexes, trigrams, badges and contact projections serve queries. Performance evidence is in [performance](performance.md).

`MIGRATIONS` in [db/migrations.ts](../packages/core/src/db/migrations.ts) is append-only. The schema version equals its length, and new migrations go at the end. As examples: 31 stores headers and word positions; 32 stores authentication results and the safe unsubscribe target; 33 stores the local optional-service switches; 34 adds message text byte sizes, a running total and an LRU index; 35 adjusts the provider ID and list date covering indexes and adds indexes for IMAP paths, orphaned remote drafts and message text sizes; 36 stores outbound retry and copy progress, claim tokens, APPEND identity and failure notices. The comments in `db/migrations.ts` explain each later entry. The read gains, write cost and disk cost of the indexes are maintained only in [performance](performance.md#写入与磁盘成本). The message text storage budget is off by default. When on, it reclaims space every hour and whenever the limit changes. It keeps retention-period mail, starred mail, drafts and the outbox first, and the limit does not guarantee room for protected content. It does not cap the whole database or all attachments. See [store-cache.ts](../packages/core/src/store/store-cache.ts).

A sync reset never deletes a message straight from a server listing. Every deletion candidate goes into a durable verification queue, and candidates that fail verification are kept. The code is in [sync-reset.ts](../packages/core/src/sync/sync-reset.ts) and [store-sync-reset.ts](../packages/core/src/store/store-sync-reset.ts), and the rule is in [ADR: sync reset verification](adr/sync-reset-verification.md). A stale cache scan with its own budget and a durable Outlook conflict check follow the same rule. Neither deletes mail just because counts differ. Deletion scope, scan budgets, the Outlook delta page size, UID identity isolation, send results and the sync health report are maintained only in [sync correctness](sync-correctness.md).

[graph-pagination.ts](../packages/core/src/providers/outlook/graph-pagination.ts) validates Graph list continuation links. It accepts only the same resource family under `https://graph.microsoft.com/v1.0/me/`, and rejects user info and fragments. When matching the resource, it accepts both slash and OData key-segment forms, any case of resource names, and well-known folder names that resolve to real IDs. The request keeps the server's URL and its opaque query. Mail and folder, contact and calendar lists share this rule. See [Outlook](../packages/core/src/providers/outlook/outlook.ts), [outlook-features.ts](../packages/core/src/providers/outlook/outlook-features.ts) and [provider-calendar.ts](../packages/core/src/calendar/provider-calendar.ts). The scope of contact traversal is maintained only in the [Microsoft setup](setup-microsoft.md#optional-services).

## Drafts and attachments

`drafts` holds editable local drafts and `messages` holds the provider mirror. A draft's local ID is `draft:<uuid>`. The remote draft or message ID is stored separately, so when Gmail or IMAP assigns a new server ID on save, the local editing identity does not change.

A user draft is saved locally first, then pushed with that draft's latest content. A queue claim stops the desktop app, the CLI and the MCP server from creating server copies at the same time. A draft opened from another client is parsed from its raw MIME through MailCodec, which keeps HTML, Bcc and attachments. The Markdown source is stored separately. Sending or discarding clears the local draft and handles the server copy. Local changes not yet pushed win over a pull.

Rules for creation logs, remote version conflicts, partial save failures and send intent recovery are in [sync correctness](sync-correctness.md#drafts-and-other-writes).

A draft a model proposes carries a `proposal_id`. Drafts from MCP and the built-in assistant stay on the Mac first. A person edits, saves or sends them in the app. The upload and approval boundaries are in the [agent guide](agents.md).

Raw messages, attachments and inline images are fetched through Mailbox. The Node `AttachmentFiles` implements a private persistent cache with atomic writes, a size limit and LRU eviction. The desktop app manages files opened temporarily. Files the user saves are separate from the cache. Body retention, backfill and cache cleanup rules are in the [release notes](release.md#old-mail-and-cache).

## Model port

`ai/model.ts` defines the streaming Model service, `ModelAnthropic` and `FakeModelLayer`. Third-party language models are separate from `ModelRuntime`, which runs local vector inference. `ai/ai.ts` is the reference for model choice.

`mailbox/mailbox-ai.ts` handles per-account text consent, keys, requests, the summary cache and triage. Per-account text consent, automatic summaries and automatic triage are off by default. The API key is stored through Secrets, and the UI reads only whether one is set. Turning consent off clears that account's AI-derived data and cancels requests. Agent tool calls read consent through `aiAccounts`, which never touches the keychain; only the Settings UI's `aiSettings` asks whether a key is set. Automatic summaries and automatic triage run only while `canTriage` is true (a focused window or AC power). Automatic summaries also stop at `AUTO_SUMMARY_DAILY_CAP` (50) and automatic triage at `AUTO_TRIAGE_DAILY_CAP` (100) per local calendar day, in the machine's time zone, counted in the `ai-auto-summaries` and `ai-auto-triage` rows of `prefs` with one upsert each, so every process shares the count. A request counts once Anthropic streamed output for it, even when it was cut off; only a request that failed before any output gives its slot back. The in-process Apple Contacts snapshot never enters these paths. See [Apple Contacts](apple-contacts.md) for the isolation.

[model-view.ts](../packages/core/src/ai/model-view.ts) and [visible-text.ts](../packages/core/src/visible-text/visible-text.ts) build the message text models see. When a message has HTML, they extract the visible text first, then strip quotes and standard signatures, and keep source IDs. Local text vectors use the same extractor. Requests to third parties contain no HTML, images, attachment bytes or media-derived content. The built-in assistant also removes attachment names and message snippets in search results, and is limited to the accounts selected for this request that have consent. Mail goes to the model as escaped JSON data, and code decides tool permissions. Hidden content, differences from the plain alternative and an exhausted CSS check budget are all marked. The limits of static extraction are maintained only in [security](security.md).

Summary and triage results live in `derived`, with the model, prompt version and input hash. A cache read revalidates them. A changed input or revoked consent invalidates the result. The UI passes the current language (BCP 47, such as `zh-CN`) to summaries, questions and compose, and the prompt asks for output in that language. The summary prompt version includes the language, so switching languages misses the cache. Background automatic summaries and triage reasons use the language from settings. When that is set to follow the system, they use the system language the desktop main process supplies. The CLI and MCP server pass no language. When the keychain cannot return the API key, `aiSettings` still returns the per-account consent and adds a `keyUnreadable` flag, so the settings page does not wrongly report that no account allows AI. Truncated output is not cached. One request allows at most 120,000 bytes of input (`AI_INPUT_BUDGET`, under 120K tokens even for CJK, inside the 1M window of every selectable model), 4 turns and 12 tool calls (`AI_TOOL_CALLS`), with a 60-second overall timeout. Every selectable model thinks adaptively, and thinking counts toward `max_tokens`, so `AI_OUTPUT` gives each feature its own output budget and effort (`output_config.effort`): triage 2,048 tokens at low effort; summaries 8,192 and the assistant 16,000 shared across its turns, at medium. Compose gets 4,096 tokens to think plus one and a half tokens per draft character, so a full 16,000-character rewrite fits, accepts up to three times the draft's UTF-8 bytes of output, and gets one more second of deadline per 50 tokens of budget. A tool call counts once however many threads it touches, so a proposal to archive 10 threads costs one call. `ToolGate` charges the call before the handler runs, and calls past the limit fail with a message saying the calls ran out. The consent check still runs on every read inside a call. A summary reads up to 80,000 bytes of its thread. When a thread is longer, the newest messages win, and the summary carries `coverage` (`kept` of `total` messages), which the app shows under it. A question reads up to 24,000 bytes per thread. When a tool result would overrun the question's budget, only that call fails: the model gets the error as a tool result and answers from what it already read. `read_thread` on the thread the question is about fails the same way, since that thread is already in the prompt.

The Cmd-J assistant uses a subset of MailToolkit. It searches local mail and any vector index that is ready, and its changes only create proposals. Compose AI uses no tools and never changes recipients. It shows generated text as a diff first and writes it into the draft once the user accepts. Further typing invalidates the earlier undo entry. Automatic triage handles at most three conversations per batch and one batch per account per minute, and runs only in the foreground or on power. Before a suggestion is accepted, it revalidates the input and the inbox state, and the user's confirmation goes through Mailbox. "Needs reply" is saved as a star.

The Indexer and semantic indexer handle local OCR, PDF text and vectors. Model downloads and inference run through platform ports. The media index switches and their output do not grant third-party AI any text permission.

## MailToolkit and entry points

`tools/tools.ts` defines `ReadMailToolkit`, `ProposalMailToolkit`, the combined `MailToolkit` and `AssistantToolkit`. Each group of tools and its handlers lives in one `tools/*-tools.ts`: accounts, threads, compose, calendar, attachments and proposals. `AgentIdentity` supplies the caller's identity and `MailToolkitLayer` reuses Mailbox. `tools/tool-pages.ts` handles cursors, result truncation and byte budgets for every tool.

`packages/cli/src/cli.ts` assembles the human commands and tool commands under `commands/`. `mcp-server.ts` exposes the same toolkit through Effect MCP. The default set contains reads and an explicit sync. Sync pulls and pushes the existing queue. Turning on write tools adds only organizing, snooze and draft proposals, which still need approval in the app. The full tool scope and call examples are maintained only in the [agent guide](agents.md).

## Desktop and tests

The desktop main process assembles NodeMailbox, system capabilities and the RPC server. `shared/rpc.ts` combines the per-domain RPC definitions in `shared/rpcs/` into the protocol, and `shared/mailbox-handlers.ts` holds the shared Mailbox handlers. The sandboxed preload bridges only JSON. The renderer queries through RPC and Effect atoms. The main entry waits for Electron's ready event. Background indexing and the first sync run after the window's `ready-to-show`.

Main process source is split by area: `app/` for startup, quit, recovery and local inference; `windows/` for windows, menus and spelling; `rpc/` for the RPC server; `security/` for protocols, external links and OAuth clients; `files/` for attachments, downloads and drag and drop; `updates/` for auto-update; `system/` for notifications, contacts, the default mail app and native compose; `remote/` for remote access over Tailscale; `agents/` for MCP mode and AI app connections. `index.ts` is the electron-vite entry. It imports `main.ts` dynamically, so a module that fails to load makes `OpenMail --mcp` print the error and exit 1 instead of showing Electron's modal error dialog. `new URL(…, import.meta.url)` resolves against the bundled `out/main/`, where the entry and its chunks sit side by side, so moving a source file does not change those paths.

Renderer source is layered, and dependencies point only downward:

| Folder             | Contents                                                                                                                                                                                                                     | Must not import                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `routes/`          | TanStack Router code routes, `router.ts` and `AppRouterProvider`. Imported only by `main.tsx` and tests                                                                                                                      |                                                 |
| `app/`             | `App.tsx`, `ThreadWindow.tsx`, panes, window shortcuts, `location-bridge.tsx` and the hooks that assemble the UI                                                                                                             | `routes/`                                       |
| `features/<name>/` | One folder per feature: mail-list, reader (with body, frame, attachments), compose, search, sidebar, organize, settings, accounts, contacts, ai, calendar, downloads, sync-status, updates, undo, overview, feedback, remote | `routes/`, `app/`                               |
| `state/`           | The RPC client, queries, mutations, events, undo and `location.ts` (atoms for the window route)                                                                                                                              | `routes/`, `app/`, `features/`                  |
| `i18n/`            | Lingui setup, `LocaleProvider` and shared strings                                                                                                                                                                            | `routes/`, `app/`, `features/`                  |
| `ui/`              | Shared React components: Dialog, Menu, Select, Toast and others                                                                                                                                                              | `routes/`, `app/`, `features/`, `state/`        |
| `lib/`             | Pure functions and generic hooks. Reads no RPC or atoms                                                                                                                                                                      | `routes/`, `app/`, `features/`, `state/`, `ui/` |

oxlint's `no-restricted-imports` enforces the table. `tests/layers.test.ts` walks the import graph from the three HTML entries (`main.tsx`, `web.tsx`, `recovery/main.tsx`) and checks three rules:

- A module loaded with `import()` is not in the graph that loads at startup.
- A feature folder's `index.ts` exports only modules that load at startup. Otherwise importing that index would pull in lazy code.
- One feature imports another through the other's `index.ts`. Modules that exist only in lazy chunks (such as `EmailFrame`, `ComposeEditor`, `OptionalServices`) are imported directly by path.

Lazy dialogs a feature opens itself go in that feature's `lazy.tsx`. `app/LazyDialogs.tsx` holds only the dialogs `app/` opens. `recovery/` is the separate entry for the recovery window. Cross-layer tests go in `tests/`, test helpers in `test-support/`, and all other tests sit next to their source. Moved files keep their names, because `bundle-split.test.ts` checks the bundle split by chunk name. Language catalogs load on demand.

In-window navigation goes only through TanStack Router code routes. The app uses hash history and tests use memory history. The routes:

| Route                   | Screen                                           | Search params                                                                                   |
| ----------------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| `/`                     | Redirects to this window's most recent view      |                                                                                                 |
| `/mail/$space/$mailbox` | The main window, `App`                           | `account`, `label` (`account/label` or a category), `q`, `scope`, `thread`, `message`, `dialog` |
| `/thread/$threadId`     | A conversation or message window, `ThreadWindow` | `single=1` shows only this message                                                              |
| `/compose/$draftId`     | A standalone compose window                      |                                                                                                 |

`shared/routes.ts` builds and parses hrefs without importing the router library, so main and renderer share it. Invalid search params fall back to defaults, and an unknown folder redirects to that space's inbox. Main uses it to build window URLs (`index.html?systemLanguages=…#/thread/x?single=1`), stores the main window's route as `href` in `windows.json`, and turns links, notifications, the tray and the Dock menu into `Navigate` events. The renderer accepts only mail routes. `app/location-bridge.tsx` syncs every history change into `locationAtom` in `state/location.ts`. The view, search, open conversation and dialogs all derive from it, and writes go through the router. Changing the view adds a history entry and writes it at once. Selecting a conversation, submitting a search and opening or closing a dialog replace the current entry. `historyFor` in `routes/router.ts` merges consecutive replaces and writes the URL once after a 300 ms pause. Chromium accepts only about 200 history writes per 10 seconds, and holding an arrow key without merging would exceed that. When a link cannot open, main sends `LinkError` and the renderer shows a notice. Transient state such as multi-select, the label picker and snooze stays in each feature's atoms.

`src/renderer/src/e2e/harness.ts` renders the real App in jsdom. It connects to a real Mailbox and a temporary SQLite database through the same RPC the preload uses and the shared handlers. Providers are fakes, and desktop windows, the clipboard and native services are stubs. It verifies mail flows from the UI to the database and the provider. Electron, real authorization and signed-build acceptance are listed separately in the [roadmap](roadmap.md). Test entry points and fault injection are maintained only in [testing](testing.md).
