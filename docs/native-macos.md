# macOS native compose features

Electron 44 can reach Writing Tools through the native menu, and Photos, grammar checking and Continuity Camera through an AppKit helper. The current Chromium has no verified entry point for macOS inline predictions. The existing AppKit helper also has no interface that returns system Markup edits. The conclusions below come from public docs and source code. The system menus, device connectivity and edit results still need acceptance on a real Mac.

The `native/`, `src/` and `build/` paths below are all relative to `apps/desktop/`.

## Version scope

This review used Electron 44.4.5, the version the repo locks. Its [DEPS](https://github.com/electron/electron/blob/v44.4.5/DEPS) pins Chromium `152.0.7977.130`. The Chromium conclusions below cover only that version. Apple APIs were checked against the public declarations in the SDK on the build machine. For minimum OS versions, each API's availability is authoritative.

## I01 Inline predictions

macOS 14 provides [`NSSpellChecker.showInlinePrediction(forCandidates:client:)`](<https://developer.apple.com/documentation/appkit/nsspellchecker/showinlineprediction(forcandidates:client:)>). The local `AppKit.framework/Headers/NSSpellChecker.h` says to request candidates with `NSTextCheckingGenerateInlinePredictionsKey` first, then hand the results to an `NSTextInputClient` to display. `NSTextView.inlinePredictionType` applies only to the matching native text view.

In the pinned version, [`RenderWidgetHostViewCocoa.h`](https://chromium.googlesource.com/chromium/src/+/152.0.7977.130/content/app_shim_remote_cocoa/render_widget_host_view_cocoa.h#51) uses `NSView` and `NSTextInputClient`, not `NSTextView`. [`requestTextSuggestions`](https://chromium.googlesource.com/chromium/src/+/152.0.7977.130/content/app_shim_remote_cocoa/render_widget_host_view_cocoa.mm#598) requests results only for the Touch Bar candidate list. It passes `options:nil` and does not call the inline prediction API above. An input method's own predictive completion is also not I01.

So the HTML `autocorrect` attribute or the system prediction switch does not prove that inline predictions work. This review found no public Electron setting and no verified Chromium flag that turns the feature on for the composer only. I01 stays missing.

## I02–I05 Writing Tools

Electron's [44.4.5 context-menu docs](https://github.com/electron/electron/blob/v44.4.5/docs/tutorial/context-menu.md#additional-macos-menu-items-eg-writing-tools) state that the extra macOS menu items are off by default. Passing `params.frame` to `Menu.popup({ frame })` enables Writing Tools, AutoFill and Services. In the pinned Chromium, [`insertText:replacementRange:`](https://chromium.googlesource.com/chromium/src/+/152.0.7977.130/content/app_shim_remote_cocoa/render_widget_host_view_cocoa.mm#2694) also handles focus loss when Writing Tools accepts a replacement. So an upstream path for writing text back exists.

The renderer draws the context menu in React (spelling suggestions, cut, copy and paste, the spell check switch). In composer message text, the React menu has one more item, "Writing Tools and Services…". When the user clicks it, the main process pops up the native menu at the click position, because these system items appear only in a native menu that has the `frame`. `apps/desktop/src/main/windows/spellcheck.ts` records the `frame` only for editable composer message text in the main frame. `ComposeEditor.tsx` marks the rich text editor and the textarea with `data-openmail-compose-body`. I02 proofreading, I03 rewrite and tone, and I05 system Compose and ChatGPT share this native entry point. The system feature, language, region and user settings still decide which menu items appear. These actions and the write-back are not verified yet, so they stay partial. [Apple Writing Tools guide](https://support.apple.com/guide/mac-help/writing-tools-write-improve-summarize-mchldcd6c260/mac)

I04 currently has only the system path for text the user selects. Apple's full range control depends on a native text view or the Writing Tools coordinator, for example `textView(_:writingToolsIgnoredRangesInEnclosingRange:)`. Electron's frame parameter does not expose these delegates. The current integration cannot exclude signatures and quotes by default, so I04 stays partial. [Apple native text view support](https://developer.apple.com/documentation/appkit/customizing-writing-tools-behavior-for-system-views)

## C51 Grammar checking and autocorrect

Electron's [session spell check API](https://github.com/electron/electron/blob/v44.4.5/docs/api/session.md) provides a spelling switch, dictionaries and language settings. It has no public switch for grammar checking or native autocorrect. In the pinned Chromium, [`allowedTextCheckingTypes` and `enabledTextCheckingTypes`](https://chromium.googlesource.com/chromium/src/+/152.0.7977.130/content/app_shim_remote_cocoa/render_widget_host_view_cocoa.mm#650) enable only text replacement, smart quotes and dashes. They do not include `NSTextCheckingTypeGrammar` or `NSTextCheckingTypeCorrection`. `autocorrect="on"` cannot fill this gap.

After the user clicks, `native/GrammarCLI.swift` calls the public [`NSSpellChecker.checkGrammar`](<https://developer.apple.com/documentation/appkit/nsspellchecker/checkgrammar(of:startingat:language:wrap:inspelldocumentwithtag:details:)>) and reads the grammar ranges, descriptions and candidates. `language:nil` uses the language selected in the system Spelling panel, so results are not promised for every language. The text reaches the local helper only through stdin. The implementation makes no network calls, writes no files and writes no logs. The composer shows marks and suggestions by UTF-16 range and replaces text only after the user confirms. One run returns at most 256 items, and the inner detail loop also checks the limit. The headless self-test uses 300 valid details to verify truncation. Each window locks the Photos helper and the grammar helper separately, so opening the photo library does not block an on-demand grammar check. The main process uses process.getSystemVersion() to limit every helper entry point to macOS 13+. This path adds on-demand grammar checking. It does not implement system autocorrect while typing, so C51 stays partial.

## M06 Photos and M07 Continuity Camera

[`PHPickerViewController`](https://developer.apple.com/documentation/photosui/phpickerviewcontroller) is available from macOS 13. Apple names PHPicker as the API that accesses only the photos the user selects, without asking for access to the whole library. The system owns the picker UI, and the app does not need to call `PHPhotoLibrary.requestAuthorization`. [WWDC22 privacy session](https://developer.apple.com/videos/play/wwdc2022/10096/?time=762)

The public docs are not enough to confirm whether a bare executable without `Info.plist` can complete the Photos picker and Continuity menu interactions. [`Bundle.main`](https://developer.apple.com/documentation/foundation/bundle/main) can return a bundle object even for an unbundled program, so it does not prove a complete app identity. An unbundled program without `Info.plist` uses the [`prohibited`](https://developer.apple.com/documentation/appkit/nsapplication/activationpolicy-swift.enum/prohibited) activation policy by default and cannot create windows. So Photos and Continuity share a minimal `OpenMailPhotos.app` that runs with a fixed app identity. This is an engineering choice. It does not prove that a bare executable must fail.

The helper sits at `Contents/Resources/native/OpenMailPhotos.app` in the released app. The main process calls its `Contents/MacOS/photos` directly and keeps the stdin and stdout protocol. `Contents/Info.plist` defines `CFBundleIdentifier=app.openmail.desktop.photos`, `CFBundleExecutable=photos`, `CFBundlePackageType=APPL`, the name, the version, `NSPrincipalClass=NSApplication` and `LSMinimumSystemVersion=13.0`. The GUI path checks the bundle ID and uses the `regular` activation policy. The helper's own layout follows the [Apple app bundle structure](https://developer.apple.com/library/archive/documentation/CoreFoundation/Conceptual/CFBundles/BundleTypes/BundleTypes.html). The outer Resources location was kept because this task required it. [Apple's code signing notes](https://developer.apple.com/library/archive/technotes/tn2206/_index.html) recommend placing nested code in locations such as `Contents/Helpers`. Code inside Resources is also sealed as a resource. The headless self-test and strict signature check do not replace acceptance of the system interactions, Developer ID signing and release notarization. These still need verification.

After the user clicks the attachment entry point, native/PhotosCLI.swift --photos opens a minimal AppKit session and picks photos with an image filter. It reads the selected content only while the item-provider callback is valid, then re-encodes the pixels as JPEG. The longest side is 4096, the target quality is 0.85, and the properties passed to the new image are nil, so it does not copy the original GPS, EXIF UserComment or other metadata. It takes the first frame and drops animation and alpha. Each input representation is at most 128 MiB. Output attachments total at most 30 MiB and at most 16 items. When one item or the running total exceeds a limit, the helper skips that item and continues with the next. The tooLarge status returns the accepted files and the skip count. The composer keeps these files and shows the over-limit notice in ten languages. Cancel returns an empty ok. A decode or read failure returns error. The main process checks the type, count, base64 and total size again.

The Photos app bundle and the grammar executable are both arm64 and x86_64 universal. Each gets an ad-hoc hardened-runtime signature with its own empty entitlements. The release signer picks the same minimal file separately for the nested Photos app and its executable, so they do not inherit Electron's JIT or Contacts entitlements. The headless self-test verifies the actual Bundle.main identity, the JPEG and size limits and original GPS removal on a 24 MP synthetic image, skipping items over the batch limit, the error statuses and the strict signature. Picking from a real photo library, canceling and the Developer ID build are not accepted yet.

Continuity Camera has a public AppKit interface and does not need direct control of the iPhone camera. Apple requires the responder to implement `validRequestor(forSendType:returnType:)` and to receive pasteboard data with `NSServicesMenuRequestor.readSelection(from:)`. The native menu item sets `NSMenuItem.importFromDeviceIdentifier`, and AppKit inserts the context menu. [Apple integration guide](https://developer.apple.com/documentation/appkit/supporting-continuity-camera-in-your-mac-app), [menu identifier](https://developer.apple.com/documentation/appkit/nsmenuitem/importfromdeviceidentifier)

`PhotosCLI.swift --continuity` provides a native receiving view this way. It reads image representations in the order HEIC, JPEG, PNG, TIFF, so it avoids first inflating to a full-size TIFF through NSImage. Images take the same JPEG re-encoding path. A read or decode failure ends the helper and returns an error status. Exceeding a limit has its own status, and the composer shows a notice. Scanned PDFs keep the original file bytes, so the image GPS removal promise does not cover PDF metadata. The phone, system settings and device connectivity decide whether the menu is available. The real-device flows for photos, scans and sketches are not verified, so M07 stays partial.

## M08 System Markup

AppKit's [`QLPreviewView`](https://developer.apple.com/documentation/quicklookui/qlpreviewview) and [`QLPreviewPanelDelegate`](https://developer.apple.com/documentation/quicklookui/qlpreviewpaneldelegate) provide preview, event and transition interfaces. The public API has no callback that enables Markup and returns the edited file. So Electron's preview support does not prove the composer can save system markup.

[`QLPreviewControllerDelegate`](https://developer.apple.com/documentation/quicklook/qlpreviewcontrollerdelegate) does have `editingModeFor`, `didUpdateContentsOf` and `didSaveEditedCopyOf`. They belong to the UIKit path for iOS, iPadOS and Mac Catalyst and cannot go straight into the current AppKit helper. Mac Catalyst API availability is not Markup acceptance by itself. The [Quick Look overview](https://developer.apple.com/documentation/quicklook) only describes preview editing on iOS explicitly. A Catalyst implementation and file write-back have not been researched or verified.

This work implements no Catalyst app, private Markup service or private selector. M08 stays missing. The reason applies only to the current Electron and AppKit integration. It does not show that no macOS helper can use system markup. Opening Preview and reimporting the file could be a separately designed external editing flow. It is not implemented and does not count toward M08.

Acceptance must keep compilation and headless self-tests apart from system interaction. This work did not start Electron, the Photos picker or Continuity Camera, and did not access a real photo library or phone. Still waiting for manual acceptance: whether the Writing Tools menu appears, its text range and write-back, content selected from the library, device photos, scans and sketches, and the signed build.

## In-window UI and native exceptions

Controls and popovers inside the window are drawn in React. Their styles come from the shared components in `renderer/src/ui/` (Select, Disclosure, Progress, Confirm, Menu). `apps/desktop/src/main/windows/native-ui-guard.test.ts` scans the source. `dialog.showMessageBox`, `window.confirm/alert/prompt`, `<select>`, `<details>`, `<progress>`, `Menu.buildFromTemplate` and `popup()` may appear only in the files listed below.

Places that stay native:

- The app menu bar, the Dock menu and the menu bar icon (tray) menu (`system.ts`). The system draws these surfaces, and there is no React outside the window.
- System notifications.
- OS file and folder pickers: export .eml, export PDF, the attachment "Save to…", and choosing the attachment folder. The renderer cannot supply a path itself. The path must come from the user's choice in the system picker before the main process writes. A plain "Save" shows no dialog. It writes straight to the attachment folder (Downloads by default) and adds a counter on name clashes as `name (2).ext`.
- The macOS share menu (`ShareMenu`), which a system service provides.
- The native menu for Writing Tools, AutoFill and Services, for the reason in I02–I05 above.
- Fallback dialogs (`native-fallback.ts`). The quit confirmation and the result of a manual update check go to the window's React first, and the renderer reports shown after it draws. When no window subscribes or no report arrives within 10 seconds, the main process withdraws the React prompt and uses a native dialog instead. If the window closes, reloads or the renderer crashes after the prompt shows, the main process treats it as cancel, so quitting does not hang. Crash and database recovery first open a separate React recovery window (`renderer/recovery.html`, with the same sandbox and CSP). If it does not draw within 4 seconds, fails to load or its renderer process exits, the main process uses a native dialog instead. The recovery flow must complete even when the renderer is broken.
- `dialog.showErrorBox` on startup failure (`main.ts`). No window exists yet at that point, and the process exits afterwards.
