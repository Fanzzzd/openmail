# Desktop security

Mail HTML, attachments, links, launch input and IPC arguments are all untrusted. The goal is to stop mail from running code, reading local files, calling the main process, or stealing OAuth tokens and AI keys. An attacker who already controls the operating system or replaces the development source is outside this boundary. Reference: the [Electron security checklist](https://www.electronjs.org/docs/latest/tutorial/security).

The OAuth loopback server (core `platform/node/oauth.ts`) accepts only GET `/` with a `state` that matches the current sign-in. A request with the wrong path, method or state gets a 404 and the sign-in keeps waiting. Examples are a favicon request, another local process or a forged `?error=`. The page HTML-escapes any provider error it echoes, and the response carries a `default-src 'none'` CSP. Cancelling sign-in in the UI interrupts the RPC, and the server closes when its scope ends. Regression tests: `packages/core/src/platform/node/oauth.test.ts`.

The main process does not enable the Node compile cache. Any process of the same user can write to the cache directory, and Node checks it only with a CRC of the source. Planted bytecode would run inside the signed main process that holds keychain tokens, bypassing ASAR integrity and the fuses.

Refresh tokens, IMAP passwords and AI keys persist only in the system keychain through core `platform/node/secrets.ts`. Removing a Gmail account first posts its refresh token to Google's revocation endpoint (`https://oauth2.googleapis.com/revoke`) through core's HTTP client with a 5-second timeout. That ends the grant, so OpenMail leaves the list at myaccount.google.com/permissions. A failed or timed-out revocation logs `token-revoke-failed` without the token and does not stop the removal. Microsoft has no per-app refresh token revocation for public clients, so removing an Outlook account deletes the token locally only; the person removes OpenMail at account.live.com/consent/Manage. IMAP has no grant. Core then deletes the keychain item and only after that the account row. When the keychain refuses (locked or denied), the account is still removed, the warning `keychain-remove-failed` is logged, and the outcome carries `keychain-item-left`; Settings and the CLI tell the person to delete the `openmail` item in Keychain Access. Code: [mailbox-apply.ts](../packages/core/src/mailbox/mailbox-apply.ts); tests: [remove-account.test.ts](../packages/core/src/mailbox/remove-account.test.ts). The renderer gets only configuration status. Built-in OAuth client values are compiled into the main process only. The renderer receives the configuration status and source, never the client values; see [release](release.md#built-in-oauth-clients). A key typed into a field travels over IPC once to be saved and never goes to browser storage. Browser storage holds only UI settings. The app has no interface that copies credentials. The main and compose window titles are fixed to OpenMail. Thread and message windows use the subject with control characters removed, at most 200 characters. The file logger in `main/main.ts` does not record raw errors. `Cause.pretty` for a startup failure goes to stderr only. Core `platform/node/diagnostics.ts` limits fields on write and on export and keeps only a hash of the account. crashReporter is not enabled and disable-breakpad is set. Memory dumps the system makes on its own follow the operating system's policy. The main process builds the system URLs for the contacts and notification settings itself. Mail cannot choose them.

The afterPack hook in `electron-builder.config.cjs` calls `build/security-fuses.cjs`. Before signing, it turns off RunAsNode, NODE_OPTIONS, CLI inspect and extra file privileges, and turns on CookieEncryption, ASAR integrity and OnlyLoadAppFromAsar. Integrity relies on the packaged build's ASAR metadata and signature. `scripts/smoke-dist.mjs` reads the fuses back from every packaged build in CI and checks that `ELECTRON_RUN_AS_NODE=1` does not run a script. See the [fuses docs](https://www.electronjs.org/docs/latest/tutorial/fuses).

macOS builds use the hardened runtime. `build/entitlements*.plist` declare only:

- `allow-jit`: needed by the Electron/V8 main process and helpers.
- `personal-information.addressbook`: for the optional local contacts feature. The app and the contacts helper declare it. Other inherited helpers do not get it.
- `disable-library-validation`: unsigned builds only, for native dependencies without a team signature. The signed configuration has no such exception. Inference runs in Electron's dedicated Plugin utility process; see `main/app/inference.ts`.
- The contacts helper has addressbook only. It has no camera, microphone, location, Apple Events or Full Disk Access.

Verification: `security.test.ts`, `rpc-security.test.ts`, `files-security.test.ts`, and the existing window, iframe, diagnostics and keychain tests. They read the built HTML, preload and JS. The fuses test flips the real fuse wire in a temporary mock binary and never touches the installed Electron. Use `OPENMAIL_LOW_MEMORY_TESTS=1`. This work did not launch Electron or build a signed installer. Runtime behavior and the signed build still need checking in the release process.

On macOS, CookieEncryption uses the system keychain. The first launch of an ad-hoc signed local build, or of a re-signed one, may ask for access to the Chromium cookie encryption key. Repeated rebuilds may ask again. This item is separate from OpenMail's OAuth and API key keychain items. Do not turn off the fuse to silence the prompt, because existing cookie storage may stop working. See [Electron cookieEncryption](https://www.electronjs.org/docs/latest/tutorial/fuses#cookieencryption).

Frame identity follows [Electron WebFrameMain](https://www.electronjs.org/docs/latest/api/web-frame-main#frameframetreenodeid) and the installed Electron 44 type definitions. frameTreeNodeId is unique within the browser and fixed for the frame's lifetime.

## Mail content protection

The visible-text filter is a CSS model without a browser layout engine. It is defense in depth only. The main defenses are the untrusted mail content envelope and human confirmation of every write. The filter treats these cases conservatively: unknown image painting, unparseable colors, media conditions and dynamic selectors, CSS nesting, pseudo-elements, filters and blend modes, overlapping paint, and an exhausted budget. It cannot prove that no hidden text reaches the model.

- Model context and text embeddings first go through `prepareMessageHtml` and `sanitizeReaderHtml`. The kept mail HTML then goes into the reader's reference shell: html, head and `body dir="auto"`. The sanitizer maps the original body attributes onto the `openmail-reader-body` container. Parsing uses [parse5](https://parse5.js.org/) HTML5 parsing, including table foster-parenting. Only the styles the reader keeps are indexed. Form controls, SVG and MathML, active content and media fallback content do not count as text. Raw structure diagnostics still count the cached HTML separately; they do not describe the rendered tree.
- Font size and visibility inherit per element and are judged at text leaves. em and percentages use the parent font size, rem the root font size. An explicit px or pt font size, or visibility:visible, can make descendants readable again. A zero-font-size container does not prune its subtree early. The font shorthand and computable calc, min, max and clamp take part. A valid but indeterminate font size, revert-layer, all, and var, env or attr are treated conservatively. Invalid declarations and non-standard important markers such as `!ie` and `!importantx` do not override a valid hiding value.
- Opacity at every level, filter opacity, and scale or zoom attenuation multiply, and the product is compared with a 0.1 threshold. The filter removes display:none, hidden and aria-hidden, content-visibility:hidden, tiny font sizes, transparent text and -webkit-text-fill-color, low-contrast text, huge offsets, constant degenerate transforms, clipping, zero size combined with hidden overflow or contain:paint, and fully transparent gradient masks. Vendor -webkit and -moz properties are normalized to standard names first. Apart from the modeled pure opacity() filter, any non-none filter or backdrop-filter and any non-normal mix-blend-mode removes the whole subtree as uncertain paint. It handles standalone scale and translate, translate transforms, rotateX and rotateY edge projection, degenerate matrices, large positive right, bottom, inset and margin-inline-start offsets, calc negative indents, and indents of -100% or less. Once an ancestor is pruned, descendants cannot restore themselves.
- color-string parses named colors, HSL, percentage RGB and 4- or 8-digit hex. HTML bgcolor and font color follow the [WHATWG legacy color algorithm](https://html.spec.whatwg.org/multipage/common-microsyntaxes.html#rules-for-parsing-a-legacy-colour-value). The background shorthand expands to background-color and background-image and shares order, specificity and important priority with the longhands. none and transparent colors show the ancestor background. Alpha colors are composited onto the parent background in the same scenario. Contrast between text and the composited effective background uses relative luminance and counts foreground alpha and inherited opacity. Below 1.5:1 the text is removed as a hiding risk. Draft loading and outgoing sanitizing use the same rule. A remote URL background uses the fallback color that shows when CSP blocks it, judged by effective contrast too. data and cid images in CSS or legacy background attributes may always load, so they count as unknown paint. Every color stop of a gradient and any huge inset box-shadow take part in the comparison. An ink or background that cannot be parsed cannot prove contrast and is removed as uncertain-paint. Partial width ranges and dynamic selectors keep hiding candidates, and colors from light, dark or other environments are never mixed.
- The reader and the filter share the default colors in reader-style, including links and mark. Color or hiding rules on ::first-line and ::first-letter make the target text uncertain. CSS nested rules are not expanded yet. A subtree that matches the outer selector is removed as uncertain-css. Within one containing block, paint checks for positioning, transforms, negative margins, outline and outset shadow do not depend on DOM order. A plain painter removes text only on an ink-color match and ignores negative margins under 10px. A replaced element counts as unknown paint only under absolute, fixed or transform, and only when its declared size on both axes is at least half the containing block, or it has explicit inset:0. Small decorative images do not count. A separate overlay rule checks explicit full-block opaque masks, opaque full-line blocks that move up and are tall enough, and thick outlines that reach into neighboring text lines. It removes only the text inside the covered area. For an inline-block or inline replaced element with a horizontal negative margin of at least 10px, whose declared width covers that shift and whose declared height fits a line, only the preceding inline siblings are checked. A replaced element there is removed as unknown paint; a known opaque background is removed as same-color-after-overlay. The margin shorthand expands to longhands first and shares order and important priority. A negative z-index takes part only as background. An inset shadow counts as background at any spread. Counting is by positioned-overlay; no browser geometry layout runs. The dark reader inverts images, video, picture, SVG image and URL backgrounds a second time. Gradients and SVG text invert once with the page.
- HTML wins over the plain alternative. A large difference is marked `plain-differs`, and removing hidden text is marked `hidden-text-removed`. When the check budget runs out it returns `budget-exceeded` and the model gets no text for that message. The search index may keep the inactive original text. Summaries and answers display as plain text, so URLs and phone numbers never become links. MCP list and search return no provider snippet. Code: [visible-text.ts](../packages/core/src/visible-text/visible-text.ts), [model-view.ts](../packages/core/src/ai/model-view.ts), [semantic-indexer.ts](../packages/core/src/ai/semantic-indexer.ts).
- When the CSS budget runs out, the fixed placeholder `[Message too complex for AI: message text omitted.]` replaces the message text. Every outgoing tool result puts mail-derived fields in `untrusted_mail` with a fixed `notice`. Quote removal recognizes In-Reply-To, matching `>` quotes, `On … wrote:`, and a complete From/Sent/To/Subject reply header block. The last two do not depend on cached mail headers. When there is no reliable boundary, removing `>` lines returns `quoted-text-removed` and the character count.
- Authentication only considers the topmost Authentication-Results header in received order. Lower headers cannot establish or override trust. Gmail requires the authserv-id `mx.google.com`. IMAP defaults to unknown. In per-account settings the user can enter the authserv-id their administrator gives them, and it must match the topmost header. The IMAP host or preset does not imply trust. Changing this setting clears the account's cached authentication results. Microsoft's format has no authserv-id. Raw header parsing accepts it only when the value starts with spf, dkim or dmarc, the first Received header's receiver is `*.outlook.com`, and the authentication header sits within the first receiving hop's header block (before the second Received, above or below the first). Any other order is unknown. Graph authentication results are currently always unknown: the delta `$select` does not include `internetMessageHeaders`. The plain message GET still fetches headers for local search, but their order does not establish authentication trust. So Outlook does not enable automatic images or one-click POST based on authentication. Authentication-Results parsing first strips nested comments and quoted strings, then splits on top-level semicolons, and keeps the last result per method. Migration 32 stores DMARC, SPF and DKIM results and the safe unsubscribe target. Old cached mail without results stays unknown. Sender names have Unicode Cf characters removed. The reader always shows the address and warns on DMARC failure and on names that embed another address. A standing image permission applies only on a trusted DMARC pass; otherwise images load per message. The remote-image default in Reading settings is "Always". When the prefs table has no `remoteImages` row, `remoteImagesChosen` is false. That field derives only from the row and is not part of `PrefsPatch`. Once the desktop app has an account, the main window shows a choice card once. Choosing or dismissing writes the row, and the card never shows again. Dismissing counts as "Always". The phone app has no card and treats an unset choice as "Ask each time". The settings page selects nothing while unset, and clicking any option records it. While prefs are not loaded or fail to load, the reader uses "Ask each time". An unparseable row also means "Ask each time". A boolean stored by an old version counts as chosen, with false meaning ask. "Ask each time" allows only allowlisted senders with a DMARC pass. "From people I know" applies only to server contacts, Apple Contacts when enabled on desktop, the account's own addresses and addresses the user has written to, and also requires a DMARC pass. So Outlook and IMAP without a trusted authserv-id never load automatically. "Always" loads for every message. Core `shouldLoadRemote` makes the decision for both desktop and phone. "Load images" allows only the messages shown at the time of the click. Messages that join the conversation later still ask. Known trackers and open pixels are removed in every mode; see the next item. cid inline images come from the cached original or the provider. They always show and never trigger the prompt. IMAP administrators must make sure the server strips incoming authentication headers with the same authserv-id. Code: [message-security.ts](../packages/core/src/reader/message-security.ts), [Gmail](../packages/core/src/providers/gmail/gmail.ts), [Outlook](../packages/core/src/providers/outlook/outlook.ts), [Node IMAP](../packages/core/src/platform/node/imap/adapter.ts), [store.ts](../packages/core/src/store/store.ts); `Reader.tsx`, `AccountControls.tsx`.
- Tracker and pixel checks run on parse results, never on regex matches of tags. `prepareMessageHtml` reads every start tag and attribute with the htmlparser2 tokenizer, so attribute names, quotes and entity decoding match the browser. It uses css-tree to read style attributes and, inside `<style>`, `url()`, image-set, image() and src() strings and `@import`. Changed tags or values are spliced back by source offset and all other bytes stay as they were. `sanitizeReaderHtml` checks again on its own htmlparser2 tree: `<img>` src, the `background` attribute, and every `Url` node inline and in `<style>`. A hit deletes the whole img or changes the value to `none`, whatever the remote-image setting. DomUtils re-serializes the sanitizer output, so the tree the browser parses again is the tree that was checked. srcset, poster, `<source>`, `<input type=image>`, and the href of SVG `<image>` and `<use>` are checked in the prepare stage, and the sanitizer then removes those attributes and elements entirely. Every URL goes through one check ([resource-url.ts](../packages/core/src/reader/resource-url.ts) `webUrl` plus [trackers.ts](../packages/core/src/reader/trackers.ts) `trackerForUrl`). It first removes ASCII tab and newline and trims C0 controls and spaces at both ends. Then it parses with the WHATWG URL parser: lowercase host, UTS-46 mapping, percent decoding, `.` and `..` segment resolution, and `https:host` and `//host` treated as HTTPS. A trailing dot is removed from the host. The path is percent-decoded by bytes up to three times, backslashes count as slashes, `..` segments are resolved once more, and then the list's path rules match. The sanitizer writes allowed remote URLs back as the parsed `href`, so the URL that loads is the URL that was checked. A remote image under 2px in width or height counts as a pixel. Size comes from the width and height attributes (by HTML dimension rules, decimals included) and from inline CSS width, height, max-width, max-height and logical size properties. Absolute and font-relative units such as px, pt and em count, and viewport units assume a 320px viewport. CSS `src()` and `attr()` with a url type always become `none`. An image shrunk only by a class or a `<style>` rule does not count as a pixel. Regression tests: [tracker-bypass.test.ts](../packages/core/src/reader/tracker-bypass.test.ts). It includes 65 payloads from review, 53 variants, and fast-check generated tag and URL mutations. With remote images on and off, it re-parses the output with parse5 to confirm no loadable tracking URL is left.
- Links opened from mail drop `utm_*`, fbclid, gclid, mc_eid and mc_cid by default. Reading settings can turn this off. Only the matching segments of the raw query are deleted and the rest keeps its byte encoding. Cleaning is skipped entirely when the URL has `X-Amz-*`, Signature, sig, signature, token, hmac, Expires, Key-Pair-Id or Policy. The browser popup exit is always denied, so nothing can skip the reader's confirmation. mailto links in mail never go to the shell, and sending still needs human review. Domain comparison uses the registrable domain and includes private suffixes. Code: [link-security.ts](../packages/core/src/reader/link-security.ts) and [email-links.ts](../apps/desktop/src/renderer/src/features/reader/frame/email-links.ts).
- Executables, disk images, macro documents, Finder location files, Windows launchers, system imports and active document extensions never go to native open, preview, openWith, share, copy or drag. Saving is still allowed. Saved and opened files get com.apple.quarantine through `/usr/bin/xattr`. Only the main process's folder picker can set a custom save folder. The renderer's SetPrefs can only reset it to ask or Downloads; a path it passes is rejected. A path saved earlier keeps working. Opening and previewing HTML and SVG goes through the EmailFrame with no scripts and no remote resources. ICS and VCF open in an in-app preview, and adding a contact or calendar event needs a separate click. iTIP invites still use the reply flow. IMAP has no calendar write access, the read-only session blocks calendar import writes, and contact import uses macOS Contacts support. Code: `main/files/attachment-filenames.ts`, `attachment-actions.ts`, `files.ts`, `attachment-folder.ts`, `main/security/file-quarantine.ts`, `shared/renderer-prefs.ts`, `AttachmentImportDialog.tsx`; core `attachment-import.ts`.
- Every provider shows a warning for invites whose organizer differs from the MIME From. A Sender header cannot outrank the real From. An unknown agent surface, or a command not on that surface's operation list, is denied by default. Code: core `invites.ts`, `policy.ts`; `InviteBanner.tsx`.
- Unsubscribe shows the target first and asks for confirmation. RFC 8058 HTTPS POST is enabled only when a trusted provider's DKIM pass maps through d (or the domain of i), s and b to exactly one signature, d aligns with the From's registrable domain, and h covers From and both unique List-Unsubscribe headers. When authentication metadata is missing, the signature is ambiguous or coverage falls short, only mailto is allowed, through a composer confirmation. With no safe path, the unsubscribe button does not show. The Node adapter resolves and pins a public DNS address, sends only `List-Unsubscribe=One-Click`, with no cookie, Authorization or redirect, and never GETs an arbitrary unsubscribe URL. The read-only session blocks POST. Other platforms without a POST adapter refuse. Code: core `message-security.ts`, `unsubscribe.ts`, `platform/node/unsubscribe.ts`; `UnsubscribeButton.tsx`. Protocol: [RFC 8058](https://www.rfc-editor.org/rfc/rfc8058).

Responsive cascade and inheritance are still computed separately at `W={720,1080}` CSS px. Only text in the same DOM text node that is visible in every environment scenario and at both widths is kept. The reference environment is screen, not print. prefers-color-scheme is computed for light and dark separately. hover, pointer, orientation and the WebKit pixel ratio used by the message are enumerated into consistent scenarios, and WebKit also covers the case where the feature is unsupported. Width conditions are evaluated exactly at each reference width. A hiding rule that does not match at the current width is not applied. So a desktop version hidden only below 600px can stay, and a narrow mobile version is excluded. The same text cannot combine visibility across two mutually exclusive nodes.

Unhiding also requires proof that the declaration matches across the whole safe range of integer CSS px from 0 to 8000. Consecutive complementary rules with the same property, value and priority can combine into a proof, so a 600/601px breakpoint pair covers the range. Partial ranges such as min-width:320px or max-width:1920px cannot unhide on their own. Within one scenario, color, background and other declarations whose conditions match enter the cascade together, and foreground and background from different scenarios are never combined. Conditions that cannot be evaluated exactly, and @supports, @layer and @container, check conservative scenarios for both match and no match. There are at most 64 environment combinations; past that the check returns the budget marker. Only type, class, id, combinators, attributes the reader keeps and static pseudo-classes can unhide. Dynamic pseudo-classes such as :read-only, :lang, :hover and :visited can only hide.

Each rule body is parsed once, with at most 8192 declarations per block. Only the properties read, the last valid value and important are kept. Match lists and per-width cascades are shared by rule ID. Display coverage merges linearly after sorting by property key. Each key has at most 256 intervals; past that limit no full coverage proof is built. Match priority is important, then selector specificity, then source order. `:where` is zero, and `:is`, `:not` and `:has` take the largest argument. Stylesheet important can override a normal inline value, and inline important wins. Semantics follow [Media Queries](https://www.w3.org/TR/mediaqueries-4/) and [CSS Cascade](https://www.w3.org/TR/css-cascade-5/).

Visible-text extraction is a conservative static CSS judgment. It does not run browser layout or external stylesheets, and it cannot prove that arbitrary CSS matches the real pixels. It does not cover overlays, element occlusion or DARK_CSS's double dark inversion, and it does not extract CSS generated content. The renderer handles dark inversion separately. Regression tests cover Gmail, Microsoft and Fastmail formats, top-level failures and forged lower passes, Authentication-Results comment and quoted-string injection, saving and revoking IMAP trust, MCP snippet removal, CSS hiding techniques, Unicode and embedded link labels, signed query preservation, and the earlier DKIM, unsubscribe, attachment and agent policy cases. They do not launch Electron or unsubscribe against a real mail service.

- Search terms and "Find in message" hits are drawn with the [CSS Custom Highlight API](https://developer.mozilla.org/docs/Web/API/CSS_Custom_Highlight_API). Core `textSearchHits` finds hits in text nodes, and the reader builds Ranges and registers them in the frame's own `CSS.highlights`. The mail DOM gets no added elements, classes or attributes. So mail CSS cannot learn the search through `:has()`, attribute selectors or counters and leak it through `background:url()`. `::highlight()` accepts only colors and text decoration and cannot load URLs. As defense in depth, selectors with `:has()` are also removed from mail CSS; the rule's other selectors stay. Showing quotes and fit-to-page still change `hidden` and inline styles. The real Chromium regression is the highlightdom case in `apps/desktop/src/main/remote/reader-frame.test.ts`. Code: [search-highlight.ts](../packages/core/src/search/search-highlight.ts), `renderer/src/features/search/text-highlights.ts`.
- The reader sanitizer drops `<link>` and `@import`. The render layer's CSP inherits the app page's `style-src 'self' 'unsafe-inline'`. The mail frame's own CSP allows only `style-src 'unsafe-inline'`, so external stylesheets do not load even when images are allowed. `url()` and `@import` inside a stylesheet would bypass the tracker and pixel filters. Regression tests: `email-frame.test.ts`.
- Recent searches live only in the local renderer's localStorage (`openmail.recentSearches`, at most 8 entries). They never go to the database, logs or sync, and removing any account clears them. Code: `apps/desktop/src/renderer/src/state/recent-searches.ts`.

## Provider diagnostics

The desktop app writes fixed fields to `OPENMAIL_HOME/diagnostics/diagnostics.jsonl`. The default data directory is in the [README](../README.md#privacy). A Gmail or Graph `provider-failure` stores only the time, provider, HTTP method, endpoint template, the status when there is one, the failure category and a 16-character SHA-256 prefix of the account ID. Search failures also store operation=search and the Graph error.code from a fixed enum; unknown codes store unknown. Deferrals write no event. It never stores the full URL, query, resource IDs, message text, error bodies, stacks or tokens. This format gives no per-command IMAP protocol log, and it does not prove the hash anonymizes.

`failure` is one of `http`, `transport`, `credentials`, `configuration` and `other`. Only a real transport failure uses status 0. A missing OAuth client is configuration and has no HTTP status. Credential failures and partial service permission gaps are handled separately. A permission 403 on an optional endpoint stops repeat requests until the user signs in again, without pausing normal mail sync. Rate limits and APIs that are not enabled are not cached by this rule.

A `reauth` event is written once when an account is marked as needing sign-in again. It holds only the time, provider, reason code and the 16-character SHA-256 prefix of the account ID. The reason codes are explained in [sync correctness](sync-correctness.md#重新登录的判定).

When sync fails, core stores only a fixed English sentence per cause: quota, auth, network, server, unknown, and for IMAP connections dns, refused, no_response, tls and unsafe_login. It never stores the provider's error body. The connection sentences match the hints elsewhere in the app and say which setting to check. unsafe_login does not retry automatically. The desktop app shows fixed translated text per cause. Raw text saved by older versions always shows as the unknown text. A `runtime-warning` with reason `sync-failed` is written at the same time. It holds only the provider (imap included), category, full or inbox scope, the status when there is one, and the 16-character SHA-256 prefix of the account ID. Code: [sync-failure.ts](../packages/core/src/sync/sync-failure.ts).

`sync-reset` diagnostics also record the provider, the listing, reset or verification phase, account and folder hashes, and counts for listed, kept, candidate, verified and deferred items. Candidate IDs are never recorded. The sync-crashed runtime-error also allows a fixed phase and causeKind and never exports exception content or stacks. RPC renderer callbacks explicitly return void, so a Fiber returned through contextBridge cannot trigger a clone error. The regression test checks JSON frames and callback return values with structuredClone. Event definitions are in [sync-reset.ts](../packages/core/src/sync/sync-reset.ts). Writing to disk and exporting use the same field allowlist.

Every warning and error log site passes a code from `LogCode` in [diagnostic-log.ts](../packages/core/src/domain/diagnostic-log.ts) through `logWarning(code, ...)` or `logError(code, ...)`. The code travels as a log annotation. The desktop logger writes it as the `reason` of a `runtime-warning` or `runtime-error` and never reads the message text. A line without a known code is `unclassified`. `diagnostic-log.test.ts` fails when source code in core, the CLI, desktop or mobile calls `Effect.logWarning`, `Effect.logError` or `Effect.logFatal` directly. Each `startup` record also carries the app version.

The export starts with one `snapshot` line, built when the feedback dialog opens. It holds the app version, the build commit, whether the app is packaged, platform, macOS version, CPU architecture, Electron and Node versions, the database `user_version` and the highest version this build supports, and the number of accounts per provider. Per account it holds the list position (not an address or hash), provider, a state enum (ok, disabled, needs-reauth, keychain-locked, sync-failed, never-synced), the reauth reason, the stored sync failure category, seconds since the last successful sync, and counts of queued changes, changes waiting out a retry delay, changes that have failed at least once, and outbox messages. Version strings must match `[0-9A-Za-z][0-9A-Za-z._+-]{0,63}`, and account entries are decoded through a fixed schema, so a path, address or error text is dropped. Code: [diagnostics-state.ts](../packages/core/src/domain/diagnostics-state.ts), `diagnosticSnapshot` in [diagnostics.ts](../packages/core/src/platform/node/diagnostics.ts), [diagnostic-environment.ts](../apps/desktop/src/main/app/diagnostic-environment.ts). Tests: [diagnostics-snapshot.test.ts](../packages/core/src/platform/node/diagnostics-snapshot.test.ts).

Each file is 256 KiB by default, with up to three rotated archives. Feedback shows an export preview and lets the user choose attachments. It creates a feedback draft and uploads nothing automatically. Old logs are re-encoded through the allowlist when previewed. RPC failures record only the method name, never arguments. Normal interruptions are not recorded. Code: [provider-diagnostics.ts](../packages/core/src/providers/provider-diagnostics.ts), [diagnostics.ts](../packages/core/src/platform/node/diagnostics.ts), [reliability.ts](../apps/desktop/src/main/app/reliability.ts) and [Feedback.tsx](../apps/desktop/src/renderer/src/features/feedback/Feedback.tsx). Regression tests: [provider-diagnostics.test.ts](../packages/core/src/providers/provider-diagnostics.test.ts).

The scope of the read-only session is maintained only in [architecture](architecture.md#read-only-session). Smoke's raw console and stderr output is not the redacted log described above. How to run the parser fuzz and accessibility tests, and their limits, is maintained only in [testing](testing.md#parser-fuzzing-and-accessibility).

## CLI and AI consent

The per-account "Allow AI to read this account" setting only restricts the agent entry points: the MCP server and `openmail tool <tool-name>`. Both call tools as `agent:mcp:<client-name>`, and consent is checked on every call. `list`, `search`, `show`, `sync` and `health`, typed by a person in a terminal, read through Mailbox as the user and see every enabled account, the same as the app. The user's own shell can read the SQLite file in the data directory directly. The CLI is not a security boundary, so checking consent there would stop nobody and would only make mail look missing. A script that reads mail on a model's behalf should call `openmail tool` or MCP.

## Connecting AI apps

"Settings → AI Access → AI apps" detects Claude Code, Codex, Claude and Cursor and reads their MCP config to work out the connection status. Reading only parses the config and never changes the file. OpenMail changes another app's config only after the user clicks "Connect", "Reconnect" or "Disconnect" and reviews the change in the confirmation dialog:

- The dialog lists the commands to run (argv) and the config file diff. The main process recomputes the change before applying it and refuses if the preview token differs, asking for a new preview. When OpenMail edits the file directly, the token is a hash of the whole file. When it goes through a CLI, only the `openmail` entry is hashed, because Claude Code rewrites other parts of `~/.claude.json` at any time.
- Claude Code uses `claude mcp add-json --scope user openmail <entry JSON>` and `claude mcp remove --scope user openmail`. `add` refuses an existing name, so reconnecting runs remove and then add-json. If add-json fails, OpenMail runs add-json again with the old entry to restore it. When `claude` is not found, the dialog only offers a command to copy.
- Codex uses `codex mcp add` to connect and `codex mcp remove` to disconnect. `codex mcp add` can write only the command, arguments and env, so reconnecting edits `config.toml` directly. When the Codex CLI is not found, OpenMail also edits the file directly. Every CLI runs through `execFile` with a fixed argv, never through a shell, with a 30-second timeout.
- A CLI exit code of 0 does not count as success. After the command runs, the main process reads the config again with `clientView`. Connecting requires the `openmail` entry's command, arguments and `OPENMAIL_HOME` to match what was expected, and `--allow-writes` to match the choice. Disconnecting requires the entry to be gone. Otherwise it reports `cliFailed` and the UI does not show "Done".
- Claude and Cursor have no CLI, so the main process edits their JSON directly. Reconnecting changes only `command`, `args` and `env.OPENMAIL_HOME` in the entry. Keys the user added (`disabled`, `autoApprove`, `startup_timeout_sec`, other env) stay. JSON edits use jsonc-parser to make minimal per-key text edits and keep the BOM. For TOML, only the text of the `[mcp_servers.openmail]` table and its subtables is replaced. Comments inside that section are not kept; everything else, comments included, stays as it was. After the edit, OpenMail parses both versions. The `openmail` entry must equal the expected one, and with it removed the rest must be identical; otherwise the edit is refused. A file that fails to parse, or an entry written as an inline table, is also refused rather than guessed at.
- Before OpenMail edits a file itself, it writes a backup next to it named `<file name>.openmail-backup-<UTC time>[-n]`, with the original permissions. It keeps the newest 5 backups per file, by time and sequence number. When a CLI edits the file, OpenMail makes no extra backup. Writes go to a temporary file in the same directory and are then renamed into place, keeping the original permissions. When the config is a symlink, the write goes to the link target and the link stays.
- The config entry holds only the command, the arguments, and `OPENMAIL_HOME` when the data directory is not the default. It never holds tokens, keys or other credentials.
- When the entry's command is an absolute path whose file no longer exists, for example a Node a version manager removed, the card points to another copy and suggests reconnecting. Besides PATH, the CLI lookup checks `~/.local/bin`, Homebrew, `~/.npm-global/bin`, Volta, Bun, pnpm, and the default fnm and nvm versions. It takes only the resolved absolute path, never the multishell directory fnm creates per shell.

The packaged app starts MCP with its own executable: `OpenMail --mcp [--allow-writes]`. The RunAsNode fuse stays off, so `ELECTRON_RUN_AS_NODE` cannot let an arbitrary script borrow the app's signature, TCC grants and keychain access. `--mcp` runs only the MCP server from the CLI package. It opens no window, shows nothing in the Dock and takes no single-instance lock. Chromium data goes to a per-process temporary directory `OpenMail MCP <pid>`, deleted on exit. At startup it removes directories left by processes that have exited, so several clients starting servers at once never share a directory. The MCP server starts after Electron is ready, because the inference worker is a utilityProcess. Development builds use `node packages/cli/dist/cli.js mcp`.

The MCP server writes one `agent_activity` row per tool call (the CLI's `openmail tool` command does not): time, client name, tool name and success. It holds no arguments or results and keeps at most 500 rows. The settings page shows recent calls per client. Code: [ai-clients.ts](../apps/desktop/src/main/agents/ai-clients.ts), [mcp-config.ts](../apps/desktop/src/main/agents/mcp-config.ts) and [mcp-mode.ts](../apps/desktop/src/main/agents/mcp-mode.ts). Regression tests: [ai-clients.test.ts](../apps/desktop/src/main/agents/ai-clients.test.ts), which use only a temporary HOME and fake CLIs.

## Remote access

A user can use OpenMail on this Mac from a browser on a phone or another computer. It is off by default and turns on in Settings → Remote access.

```
Phone browser ──WireGuard (tailnet)──▶ Tailscale app on the Mac
                                     │  tailscale serve --https=8443
                                     │  adds Tailscale-User-Login / -Name, keeps Host
                                     ▼
                     OpenMail main process http://127.0.0.1:<port>
                       ├─ GET /, /assets/*    out/web static files
                       ├─ GET /api/attachment attachment download
                       ├─ POST /api/upload    attachment upload
                       └─ WS /rpc             RemoteRpcs (Effect RPC)
                                     ▼
                                 packages/core
```

The main process only handles transport: HTTP, WebSocket, sessions and Tailscale CLI calls. Mail logic stays in core, and remote RPCs reuse `shared/mailbox-handlers.ts`. The code is in `main/remote/`.

### Publishing

- OpenMail first looks for the Tailscale app's bundled `/Applications/Tailscale.app/Contents/MacOS/Tailscale`. Then it looks for a separately installed CLI at `/opt/homebrew/bin/tailscale`, `/usr/local/bin/tailscale` and `tailscale` in the absolute-path directories on `PATH` (`tailscaleCandidates` in `tailscale.ts`). They all talk to the same tailscaled, so `status`, `serve` and identity headers behave the same. Every call uses `execFile` with a fixed argv, never a shell. OpenMail installs nothing. When none is found, the settings page links to tailscale.com/download.
- Before turning on, it checks in order that Tailscale is installed, signed in, and that the tailnet has HTTPS certificates (`CertDomains` in `status --json` is not empty).
- It reads `serve status --json` first. If port 8443 is already taken by another mapping, a TCP forward, a foreground serve or Funnel, it refuses and overwrites nothing. Then it runs `tailscale serve --bg --https=8443 http://127.0.0.1:<port>`.
- Turning off runs `tailscale serve --https=8443 off`, and only when the mapping points at this app's port. If `serve status` or `serve off` fails, for example because Tailscale is not running, it does not report "off". The status is `error` with the problem `removeFailed`, and the settings page says the mapping could not be removed. The controller remembers the mapping and retries after 30 seconds (`RETRY_MS`), doubling the wait up to 5 minutes (`RETRY_MAX_MS`), and on every Refresh. Once Tailscale is back, it removes the mapping with the same ownership check.
- The read-only session (`OPENMAIL_READ_ONLY=1`, used by smoke for example) never runs the Tailscale CLI. It treats Tailscale as not installed and neither publishes nor removes mappings (`sessionTailscale`).
- If the setting is off at startup but a port was saved (the last run may have crashed while on), it checks once the same way and removes a mapping that points at this app's old port. If Tailscale is unreachable, it reports no error and retries in the background.
- Quitting the app removes the mapping too, waiting at most 3 seconds (`QUIT_TIMEOUT_MS`). The setting stays on, and the next launch publishes again. Otherwise, while the app is closed, the mapping would point at an empty loopback port, and another local process or another macOS user could take the port and receive tailnet traffic and identity headers. If the wait times out or the CLI fails, the mapping stays, and at the next launch `serve status` recognizes it as this app's old mapping and replaces it.
- The serve target is TCP loopback only. The macOS GUI Tailscale is a sandboxed network extension and most likely cannot read a unix socket in the user's home directory. The target will not switch to a socket before that is tested.
- OpenMail never runs `tailscale funnel`. If `serve status` shows `AllowFunnel` for the port, it refuses to start.
- An optional Tailscale Service (such as `svc:openmail`) uses `serve --service=svc:openmail --https=443` instead.

### Per-request checks

`checkRequest` (`remote-auth.ts`) checks these in order. Any failure returns 403 or 421:

1. The TCP source is loopback. The server listens only on 127.0.0.1; this check guards against a wrong listen address.
2. There is no `Tailscale-Funnel-Request` header.
3. There is a `Tailscale-User-Login` header. Serve adds it only for devices in the tailnet that belong to a user. Direct local access and tagged devices have none, so they are rejected.
4. `Host` equals `<magicdns>:8443` (or the Service's host name). This blocks DNS rebinding.
5. The login is in the allowlist, case-insensitively. By default the list holds this Mac's own tailnet login, written once the first time remote access turns on. It holds at most 64 logins.

WebSocket upgrades and uploads also require `Origin` to equal `https://<host>`.

Until start-up has confirmed the Serve mapping and set the gate, every request and upgrade gets 503 with `Retry-After: 2` and no cookie. The page reads 503 as offline and keeps retrying; only 401 and 403 end its session.

### Sessions

The Tailscale identity is the credential. A session only ties one browser's WebSocket, downloads and uploads to its login, so they can be listed and disconnected.

- App pages (paths without an extension) and the session check `GET /api/session` issue `__Host-openmail-session`. Static assets and 404s do not. The cookie is HttpOnly, Secure, SameSite=Strict, Path=/. The value is a random id plus an HMAC, with a key regenerated at every launch.
- The page calls the session check before every reconnect. A request that passed the identity gate but has no live session gets a new one there, as a page load would give it. So restarting the Mac app does not sign phones out: on quit the server closes WebSockets with 1001, and pages reconnect when the app is back. The check refuses to issue a cookie when `Sec-Fetch-Site` is present and not `same-origin`, so another site can't mint sessions through the person's browser. A live session gets its cookie again with a fresh Max-Age.
- A session is bound to a login and expires 12 hours after its last request. A session with an open WebSocket does not expire. Sessions live in main-process memory. A request whose login differs from the session's login is rejected. There are at most 50 sessions; past that, the least recently used session without an open WebSocket ends, or the least recently used one when every session is connected.
- The server sweeps expired sessions every 60 seconds.
- Disconnect on the settings page ends one session and closes its WebSocket (close code 4401). The server remembers the ended session id until the session would have expired, so the session check answers 401 and the page waits for the person instead of reconnecting. A session ended by the 50-session limit is remembered the same way. Turning remote access off ends every session with 4401. As long as the login is still in the allowlist, reloading the browser gets a new session, and the page says so. The record of ended sessions is in memory: after a restart, a browser that was offline when it was disconnected gets a new session at its next check, which a reload would give it anyway. To really deny someone, remove their login from the allowlist. Their sessions end at once and every later request is rejected.

### Remote RPC table

`REMOTE_RPC_POLICY` in `shared/remote-policy.ts` lists the allowed RPCs, and `RemoteRpcs` in `main/remote/remote-rpcs.ts` is built only from them. An RPC not in the table has no handler on the remote server. The request is rejected and logged. `remote-rpcs.test.ts` pins the full allow list and the list that must be denied, and asserts that a new RPC is denied by default.

The web build reads the same table. `canCall(tag)` in `lib/platform.ts` is always true on desktop, and in the web build is true only for RPCs in the table. A control that would call a denied RPC is hidden based on the RPC it calls. For example, "Sign in again" becomes "Sign in again on your Mac" on the web.

Allowed: reading, search, compose, send (the same outbox and undo send as desktop), organizing (archive, labels, snooze, delete), contact suggestions, calendar invite replies, and the mail and UI preferences in `REMOTE_PREF_KEYS`.

Denied: local files and Finder, opening the browser, printing, windows, the clipboard, OAuth and adding accounts, the keychain, MCP and AI keys, updates, quit and restore, the default mail app, Apple Contacts, and the remote access settings themselves.

`OPENMAIL_READ_ONLY=1` takes effect in core's provider layer, so remote writes are blocked too. Remote send adds no extra confirmation and goes through undo send, the same as desktop.

### Attachments

- Download: `GET /api/attachment?message=<id>&part=<path>`, which needs a session. The response has `application/octet-stream`, `Content-Disposition: attachment` and `Content-Security-Policy: sandbox`, so the browser never renders an attachment on this origin.
- Upload: `POST /api/upload?account=<id>`, which needs a session, Origin, an existing account and Content-Length (411 when missing), so the account's type check always runs. The limits match desktop: 30 MB in total, and 415 for types Gmail rejects. At most two uploads run at once; more return 503. The body is read into one buffer of the declared length, parsed, and handed to core as base64.

### Browser pages

- `out/web` is a second Vite build of the same renderer, with entries `renderer/web.html` and `renderer/src/web.tsx`.
- Response headers: `default-src 'self'`, `connect-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`, plus `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store` (app pages).
- The mail iframe is the same as on desktop: `sandbox` has no `allow-scripts`, and the CSP inside the iframe blocks remote resources.
- Static files are confined to `out/web` by realpath. Traversal and symlinks that point outside are rejected.

### Outside the boundary

- Local processes of the same user can connect to 127.0.0.1 directly and forge Tailscale headers. They can already read the database and the memory of processes with keychain access, so they are outside this boundary. Web pages in a browser cannot send custom headers cross-origin, and the Host check blocks DNS rebinding.
- A login in the allowlist can sign in from any tailnet device that belongs to that user. Restricting devices needs tailnet access policies.
- If removing the mapping times out or fails on quit, the mapping stays until the next launch. The port-takeover risk during that time is described under [Publishing](#publishing).
- Disconnect cannot block a login that is still in the allowlist; see [Sessions](#sessions).
